## Context

写作流水线已经把章节摘要、钩子记录、卷汇总和段汇总写入本地数据库，但工作台缺少统一入口。现有阅读接口只返回章节列表中的简要摘要；正式工作台使用的类型化 HttpApi 还没有覆盖这组只读数据。右侧检视面板已经有角色、伏笔、节奏、结构和批注入口，新增一个同级入口最贴近当前布局。

## Goals / Non-Goals

**Goals:**

- 为工作台提供一次加载 AI 产出数据的类型化只读接口。
- 在检视面板中新增 AI 产出分区，覆盖章节摘要、钩子轮换、卷/段汇总。
- 保持查询侧实现简单，不做数据迁移和写入能力。

**Non-Goals:**

- 不修改状态提取、observer、卷汇总或段汇总的生成逻辑。
- 不提供 AI 产出的编辑、删除、重算或大屏可视化。
- 不把独立阅读页改造成完整的 AI 产出管理面板。

## Decisions

### D1: 新增一个聚合查询端点

在小说 HttpApi 中新增 `GET /novels/:novelID/ai-artifacts`，一次返回四类只读数据：

- 章节摘要：章节序号、标题、摘要和关键事件。
- 钩子数据：最近记录、类型统计和连续重复警告。
- 卷汇总：汇总正文、活跃/休眠角色和开放/关闭线索。
- 段汇总：章节范围和汇总正文。

选择聚合端点而不是四个细端点，是因为这些数据只在同一个检视视图中展示，一次查询可以减少面板状态同步成本。协议 schema 定义在 `packages/protocol`，服务端只做查询和映射；实现后从 `packages/client` 运行 `bun run generate` 重新生成 SDK。

### D2: 检视面板使用同级新标签

在右侧检视面板新增 `AI 产出` 入口，与角色、伏笔、节奏、结构、批注同级。面板内用三个分区展示数据，不嵌入章节正文编辑器。

这样能保留“检视 AI 理解结果”的独立心智；比起塞进章节详情，能避免编辑器进一步变重。选中章节仍可作为定位上下文，用于查看对应摘要和钩子。

### D3: 服务端聚合和映射数据

服务端复用现有本地数据库表查询：章节摘要关联章节取标题和序号，卷汇总关联卷，段汇总按起始章排序，钩子记录按时间倒序。JSON 字段在服务端映射为类型化数组；章节不存在时沿用现有 `NovelNotFoundError` 行为。

钩子统计在查询时从记录汇总得到，连续重复警告保持与写作链路相同的时间窗口语义，避免前端重新解释业务规则。

### D4: 前端保持只读并直接渲染

新增 SolidJS 查询 hook 和面板组件，按加载中、失败、空状态和正常数据渲染。组件不提供任何写入控件。该提案暂不改 i18n locale 文件，新增面板文案在组件内使用简体中文常量；后续如需多语言扩展，再单独整理 key。

### D5: 数据刷新跟随查询生命周期

打开面板、重试或切换小说时重新查询。面板不做实时推送；流水线执行过程中不强制刷新，用户返回检视时或点击重试即可看到最新已提交数据。

## Risks / Trade-offs

- [长篇小说的章节摘要数量较多] → 聚合响应按章节序号返回当前存量摘要；面板分区懒渲染或限制初始展开范围，避免一次性展开全部长文本。
- [钩子统计口径与写作链路不一致] → 沿用现有最近窗口和类型定义，服务端负责统一计算。
- [未改 i18n 文件导致后续多语言缺口] → 新组件集中放置文案；后续若开放 locale 修改，再迁移到语言 key。

## Migration Plan

1. 新增协议 schema 和端点，运行 SDK 生成。
2. 新增服务端聚合查询与映射。
3. 新增前端查询 hook 和 AI 产出检视面板。
4. 运行相关包测试、全仓 typecheck、lint 和 OpenSpec 校验。
5. 回滚方式是移除该只读端点和面板入口，不影响既有数据表。
