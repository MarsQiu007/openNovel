## Context

当前手动 UI 写入主要由 `packages/server/src/handlers/novel.ts` 直接更新正式表；AI 写入则由 `packages/plugin` 的状态提交、引用扫描、设定影响和上下文组装模块维护派生数据。`packages/server` 不能依赖 `packages/plugin`，但 `packages/opennovel` 已经组合 Server 与 Plugin，可以在进程内把两者接起来。

主要约束：

- 章节自动保存频繁，不能为每次输入都同步执行昂贵 LLM 任务。
- 既有 SQLite 数据没有统一的派生数据来源指纹。
- `novel-store` 不依赖 plugin；通用队列和新鲜度元数据可以放在数据层，AI 重建逻辑留在 plugin。
- 公开 HttpApi 的入参或返回值变化后，必须重新生成 client SDK。

## Goals / Non-Goals

**Goals:**

- 为所有手动编辑入口建立可审计的分类和同步策略。
- 把“保存成功”和“AI 已感知”变成两个可查询、可展示的状态。
- 复用现有状态提交、引用扫描、设定影响和写作门禁能力。
- 保持旧数据库可读、可导出、可继续编辑。

**Non-Goals:**

- 不把纯 UI 偏好提升为创作事实。
- 不在上下文组装时同步执行长耗时 LLM 重建。
- 不重新设计写作流水线的阶段划分。
- 不自动执行需要语义确认的设定改写。

## Decisions

### 1. 采用“服务端持久化 + plugin 后台同步”的两段模型

`packages/server` 的手动编辑 API 负责用户操作的可靠落库，但必须在同一事务中创建同步请求或过期标记；它不依赖 Plugin，只产出通用同步请求。随后 `packages/opennovel` 启动手动编辑同步 worker，消费队列并调用 plugin 中的引用扫描、状态提取、影响任务和派生数据重建能力。

选择两段模型而不是把 LLM 同步塞进 HTTP 请求，是因为章节自动保存需要快速返回，而且摘要重建可能失败、重试或需要批量合并。选择后端队列而不是前端触发，是因为前端包装器无法约束外部 API 调用，也不能保证 AI 工具和 UI 使用同一规则。

### 2. 用编辑目录统一分类

在服务端维护一个静态编辑目录，描述每个手动 API 的实体、字段、数据类别和同步策略：

```text
creative_fact   → 必须可进入 AI 上下文或写作门禁
workflow_fact   → 只进入对应流程，例如审批、审计、批注执行
ui_preference   → 只影响界面，不进入写作上下文
```

目录是服务端权威配置；UI 只读取结果状态，不自行决定某个字段是否需要同步。这样能避免每个面板复制一套判断。

### 3. 派生数据使用来源指纹判断新鲜度

章节摘要、实体引用、受影响段摘要和故事主轴条目记录来源正文指纹。指纹不匹配、缺失同步记录或历史数据没有指纹时，统一显示为待校验/待同步，而不是假定最新。

章节正文同步完成后，章节摘要和实体引用可以重建；只有受影响范围内的段摘要需要重建。故事主轴新增结构化条目数据，按章节保存正文指纹和主轴内容，`novels.story_spine` 保留为兼容渲染缓存。

### 4. 设定修改在事务后立即执行确定性影响

角色、世界观、关系、剧情线、伏笔等设定保存成功后，同步 worker 先执行确定性引用扫描和影响任务生成；这一步不需要 LLM。需要语义建议或生成式改写的部分仍进入既有待确认影响任务，不自动改章节。

### 5. 正文记忆同步由 observer 语义重建

手动正文同步任务合并同一章节的连续编辑后，调用既有 observer/状态提取路径重建摘要和引用，并生成新的状态候选。任务失败时保留失败原因和重试入口；用户明确跳过后，该项不再单独阻塞写作，但状态保持可追溯。

### 6. API 语义与 SDK

需要调整的公开契约包括：

- 编辑目标不存在时返回明确 404 类错误，禁止静默返回旧列表。
- 新增手动编辑同步状态查询。
- 新增或改造书籍元数据 + 风格指南的联合保存端点，避免同一表单调用两个独立 API 造成半提交。
- 编辑响应如需携带同步状态，统一放在可扩展的 `sync` 字段中。

这些契约变化后，从 `packages/client` 运行 `bun run generate` 重新生成 SDK；不手改 generated 文件。

### 7. UI 只显示状态，不复制同步规则

工作台编辑器统一展示保存中、已保存、保存失败、待同步、同步失败和已跳过。章节自动保存失败必须覆盖“自动保存成功时间”，并保留重试按钮。多字段表单调用联合端点；不再通过串行 mutation 模拟原子保存。

## Risks / Trade-offs

- [手动正文同步消耗 LLM 成本] → 同一章节任务按来源指纹合并，编辑停止后延迟执行；自动保存只更新队列状态，不逐键触发模型。
- [结构化主轴迁移可能无法完美解析旧文本] → 旧文本先迁移为 legacy 条目并标记待校验，不伪造章节来源；新写入一律走结构化条目。
- [影响任务过度生成造成用户疲劳] → 使用稳定键去重；只有标题、关键定义、关系类型、生命周期等受控字段触发联动，纯排版或空白变化不触发。
- [后台同步失败导致写作被阻塞] → 提供失败原因、重试和显式跳过；只有影响当前写作范围的阻塞项才参与门禁。
- [API 返回结构膨胀] → 同步状态作为可选扩展字段，旧客户端可继续读取原有业务字段。

## Migration Plan

1. 先新增可空同步元数据和队列表，所有旧数据保持可读。
2. 服务端逐步把手动编辑端点切换到统一目录和事务辅助层，先处理章节正文、正式设定和多字段书籍保存。
3. `packages/opennovel` 启动同步 worker，消费新队列；旧派生数据按“缺指纹 = 待校验”处理。
4. UI 分批接入保存状态和联合保存端点。
5. 公开契约稳定后运行 `bun run generate`，再执行受影响包 typecheck、测试和 HttpApi exercise。

回滚时保留新增表和可空列即可；禁止删除旧正式数据。队列可作为无效数据停用，不影响既有读写路径。
