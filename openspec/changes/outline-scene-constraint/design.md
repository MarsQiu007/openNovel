# 设计：章纲场景约束（prompt 层）

## 背景与根因

见 proposal.md。核心判断：章纲场景对 writer 是「参考」而非「约束」——

```
  章纲 markdown（关键场景 4 段，纯文本）
     │  现状：原文超 1.5K tokens 时被 budget.ts 截到 2200 字符
     ▼
  writer 读「参考」→ 自由发挥 → 无任一环节拦截偏离
```

业界做法（网络探测结论）：不是把大纲写更好，而是「加载 + 对照」——dispatch 时把大纲编译成显式「必须发生事件清单」注入 prompt，把参考性输入升级为硬约束。

## 方案

### 1. 确定性编译器 `compileSceneChecklist`

新文件 `packages/plugin/src/novel-writer/scene-constraints.ts`，导出纯函数：

```ts
compileSceneChecklist(outlineMarkdown: string): string | null
```

解析规则（对 LLM 填充的章纲 markdown 保持容差）：

- 以 `## 关键场景` 为入口，按 `### 场景…` 标题切分场景段（场景一~四，标题文案不固定，按前缀 `### 场景` 匹配）。
- 每个场景段内按 `- **字段名**：值` 提取 地点/时间/出场角色/场景概要/字数预估；字段值为空或「（待填写）」时跳过该字段，不输出空条目。
- 每个场景输出固定条目：

```
### 场景N：<场景标题>
- 地点：…
- 时间：…
- 出场角色：…
- 必须发生：<场景概要原文>
- 字数预估：…
```

（「场景概要」在清单中改名「必须发生」，语义从参考升级为义务。）

- 一个场景段都切不出来 → 返回 `null`；调用方不输出清单段，writer 退回现有参考性行为。**解析失败永不阻塞写作**。

### 2. 清单的编译时机与携带方式（关键决策）

`budget.ts` 的 `applyChapterOutlineBudget` 在章纲超 1.5K tokens 时将其截到 2200 字符。若在快照渲染时从（可能已裁剪的）`chapterOutline` 编译清单，会得到**残缺清单被当成完整硬约束**（例如只剩场景一/二），比没有清单更糟。

因此：

- `recall.ts` 的 `assembleWriterSnapshot` 在取得完整章纲原文（`resolveChapterOutline` 返回、预算裁剪发生之前）即调用 `compileSceneChecklist`，结果存入快照包新字段 `ContextPacket.sceneChecklist: string | null`。
- `sceneChecklist` **不参与任何预算裁剪**（硬约束完整性优先于 token 预算），与 `prevChapterTail` 的豁免策略同理。
- `context.ts` 的 `formatSnapshotToolOutput` 只负责渲染：字段非空时在「═══ 本章大纲 ═══」段之后追加：

```
═══ 章纲场景硬约束清单 ═══
本章正文必须逐场景落实以下清单。清单与字数、角色白名单同为硬约束。
<清单内容>
```

- `ContextPacket` 新字段为可选；`scale-test.ts`/`rollup.ts` 的 mock 构造不传该字段时行为与现状一致。

### 3. 注入点二：read_outline 兜底（novel-writer.ts）

`read_outline` 工具 `type=chapter` 返回正文时，对**未截断的**正文调用同一编译函数，结果非空则在正文后追加同一段。保证 pipeline 章纲保障兜底路径（快照缺章纲 → read_outline）与主路径行为一致。

### 4. writer 硬规则（writer.ts）

写作规则区新增一条硬规则（接在第 31 条之后），核心语义：

- 正文中每个清单场景必须出现，且顺序与清单一致；
- 清单列出的出场角色必须实际出场；
- 「必须发生」列出的场景概要事件必须在正文中落地；
- 禁止静默跳过、合并或调换场景顺序；
- **显式偏离出口**：若判断某场景与前后文矛盾、确需偏离，必须在返回 pipeline 的报告中逐条列出偏离的场景、实际写法与理由。静默偏离即违规。

同时更新规则区总条数（「以下 31 条」→ 实际条数），并在工作流程第 6 步自检清单中追加「逐场景覆盖核对」一项。

与现有规则的边界：

- 与规则 30（正文纯净，禁止复制场景标题）互补：清单是内部约束，场景标题仍不得进入正文。
- 与规则 29（结构线/弧光推进）互补：规则 29 管弧光节点推进，新规则管章纲场景落实。

### 5. pipeline dispatch 指示（pipeline.ts）

步骤 3 dispatch prompt 指示 ① 处追加：快照或兜底输出中的「章纲场景硬约束清单」为必须逐条落实的硬约束；writer 生成后须按清单逐场景核对后再调用 write_chapter。

## 关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 编译时机 | 快照组装时编译（预算裁剪前），渲染时只输出 | 避免从被截断的章纲编译出残缺清单被当成完整硬约束 |
| 预算裁剪 | 清单独立字段、不参与裁剪 | 硬约束必须完整，完整性优先于 token 预算 |
| 存储 | 运行期派生文本，不落库 | 落库带来 schema 迁移与同步成本；章纲更新后下次 dispatch 自动拿到新清单 |
| 编译失败行为 | 静默降级（不输出清单段） | 解析失败阻塞写作代价远大于收益；无清单时退回现状（参考性输入） |
| 偏离处理 | 显式声明出口，而非绝对禁止 | 章纲本身可能与前文矛盾；把「偏离」从隐性变显性，为后续审计提案提供对照锚点 |
| 规则落点 | writer 系统提示词规则区 + pipeline dispatch 指示双写 | 与现有「字数硬约束」的落实方式一致（规则 16 + dispatch 指示 ②） |

## 与后续提案的关系

后续审计提案（outline-scene-audit，暂名）将：auditor/continuity-check 新增「章纲场景覆盖」维度，消费 `compileSceneChecklist` 的同一份输出对照正文逐场景判定，FAIL → reviser 定向修订。本提案固化的清单格式即为其对照基准，两提案通过该函数解耦。
