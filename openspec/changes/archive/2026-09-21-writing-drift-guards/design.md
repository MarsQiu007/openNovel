## Context

writer 有世界观硬约束规则，但缺少统一的命名角色与关系约束。auditor 虽然定义了关系连续性维度，却没有强制读取关系权威数据；轻量设定审计也不保证覆盖关系维度。observer 提示词要求读取关系，但状态提交流程对关系引用的解析和冲突兜底不足。

本提案依赖 `relationship-hard-context` 输出的方向化关系、亲属称谓绑定和未解析标记。

## Goals / Non-Goals

**Goals:**

- 给 writer 提供统一的“命名角色 + 关系派生称谓”约束视图。
- 让关系数据成为 auditor 的必读权威来源。
- 让 observer 在状态提取阶段优先解析既有角色，避免把称谓固化为新角色。
- 使用候选区承接无法唯一解析或存在冲突的情况。

**Non-Goals:**

- 不追求识别所有隐式代词和任意别名。
- 不自动合并或删除疑似重复角色。
- 不修改公开 API、数据库 schema 或历史章节。
- 不保证一次性消除所有模型自由发挥；目标是让漂移可被发现并阻止其进入正式设定。

## Decisions

### 1. 复用并传递角色绑定视图

建立一个内部角色绑定视图，输入包括：

- 既有角色名。
- 关系方向解析产生的亲属称谓。
- 当前活跃状态与章纲相关性。
- `relationship-hard-context` 标记的未解析称谓。

该视图会进入 writer 上下文、审计输入和 observer 的提取辅助数据。不新增通用角色别名表，也不承诺识别任意昵称或代词。

### 2. writer 使用保守命名规则

writer 上下文和提示词将明确：

- 有正式名的角色在叙事主体中应使用正式名，或明确绑定“正式名 + 称谓”。
- 不能把已有关系中的亲属称谓写成一个新的、无绑定的角色名。
- 章纲明确要求新增角色时除外。

不禁止“儿子”一词本身。对话中称呼“儿子”、内心称呼亲属称谓仍应允许；限制的是把称谓实体化为新的未命名角色。

### 3. 写入守卫只做保守确定性检查

章节提交前增加低成本检查：

- 识别关系派生称谓附近的“是/叫/名为/成为”等实体化表述。
- 如果该称谓能唯一绑定既有角色，检查正文是否使用了既有角色名或明确绑定。
- 如果无法唯一绑定，则不直接判定章节失败，而是生成审计提示，由 auditor 继续判断，状态提取再进入候选区兜底。

备选方案是在写入工具中用 LLM 预审全部正文。虽然覆盖面更广，但会重复审计成本并增加延迟，因此不作为第一层。

### 4. auditor 必读关系数据

auditor 前置动作增加读取角色关系。pipeline 在派发审计时显式传入当前快照中的受保护关系和角色绑定视图。

- 全量审计必须检查关系连续性维度。
- 设定一致性专项审计也必须包含关系连续性维度。
- 关系 FAIL 必须引用正文证据和权威关系证据。

### 5. observer 与状态提交共享解析结果

observer 继续先读取角色和关系。状态提交阶段在处理角色或关系前先复用角色绑定视图：

- 本地 entity id 可解析到既有角色时更新既有角色。
- 亲属称谓唯一匹配时绑定既有角色。
- 多个候选或零候选时不自动创建正式角色，而是进入候选区。
- 新强关系与既有强关系冲突时生成带冲突原因的候选关系，不自动覆盖。

现有冲突表语义是世界观条目冲突；为避免在本提案中扩展数据模型，关系冲突先用候选关系的 payload 记录冲突原因和原文证据。

## Risks / Trade-offs

- [确定性写入守卫可能漏检隐式漂移] → 交给必读关系数据的 auditor 和 observer 候选区兜底。
- [称谓解析过严可能产生额外候选] → 候选区成本低于错误设定入库，后续可人工接受或拒绝。
- [审计上下文变长] → 只传入相关关系和绑定视图，不传全量历史章节。
- [observer 判断依赖提示词遵循度] → 状态提交侧仍做机械解析和候选兜底，不只依赖模型自觉。

## Migration Plan

- 不迁移数据库。
- 旧章节中已经存在的错误候选和关系不自动清理；用户可继续使用现有去重/合并工具。
- 新流程上线后，未解析称谓只会进入候选区或审计提示。
- 回滚时恢复旧审计调度和状态提交路径，不影响已有数据。
