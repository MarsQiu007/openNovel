# Design

## Context

当前 tool-insight 的启动对账、索引重建、锁目录创建和复测临时 Location 都会在没有真实问题时产生工件。事件采集又按插件实例运行，多个 Location 可能同时消费同一批全局会话事件；现有去重只发生在问题文档内，JSONL 证据层本身没有唯一性约束。
用户负反馈目前只能通过显式 `/evaluate` 入口进入 `tool_insight`，普通对话中的「不对 / 错了」不会形成可聚合信号。

相关实现分布在 `packages/plugin/src/tool-insight`、`packages/novel-store/src/evaluate-insight.ts`、`packages/plugin/src/novel-writer-v2.ts` 和复测编排模块；日志仍保持本地文件形态，不新增数据库表。

## Goals / Non-Goals

**Goals:**

- 把空状态、索引、锁和日志根的创建收敛到「有真实记录才落盘」。
- 让复测临时 Location 不再污染共享日志目录。
- 用稳定标识在存储层去重，防多实例与崩溃恢复重复追加证据和信号。
- 将会话/项目归属作为日志根和事件归属的依据，而不是把所有事件都复制到每个活跃 Location。
- 把「不对 / 错了」这类负反馈变成低噪声信号，并提供显式确认升级为 `user_report` 的路径。

**Non-Goals:**

- 不重写问题文档格式，不引入数据库表或云端上报。
- 不自动删除旧目录中的历史空根；旧数据只读兼容。
- 不把每日汇总作为新的 source of truth。
- 不让负反馈信号层保存完整对话原文、完整章节正文或绕过现有隐私白名单。
- 不改变写作反馈意图协议在正文修订中的既有职责。

## Decisions

### 1. 空状态探测先行，落盘按需创建

启动对账先读取现有日志根、证据文件、问题目录、复测记录和信号文件；只有发现真实记录、可修复损坏尾部或待处理任务时才进入锁与重建流程。日志根、锁目录、索引和各类数据文件只在写入第一条真实记录时创建。索引保持派生视图：没有问题文档时不写空索引。

选择这种方案而不是「启动时统一初始化」，是因为后者会把健康状态也变成可见噪音。备选的「保留空索引以便 UI 显示」不必要，UI 可以把缺文件视为零问题。

### 2. 日志根按会话项目归属解析

事件采集时先从 `session.next.created` 维护会话到项目目录和 projectID 的最近使用映射；证据和负反馈信号按该归属解析日志根，而不是按每个插件实例的 Location 解析。
未观察到创建事件时，可查询持久会话归属，但只有其目录与当前插件装载位置一致才允许兜底；临时复测 Location 或无法确认归属的会话仍不采集。
这样同一事件只会写入同一个项目根，避免多个 Location 复制，也沿用既有按项目目录哈希隔离的兼容策略。`tool_insight` 主动记录入口也使用同一会话项目目录解析，避免手动记录与自动采集分裂到不同根。

选择会话归属而不是进程级单例，是因为后者无法覆盖桌面端与 CLI 并存的多进程场景。日志根仍然保留项目隔离语义；`global` 会话只进入专门的全局根，不会复制到每个小说项目根。

### 3. 复测临时 Location 带 internal purpose 标记

`startBackground(mode: "retest")` 已经登记 tool-insight purpose；把这个 purpose 传播到临时 Location 的插件上下文中，插件在启动时识别该标记并跳过常规采集、负反馈信号采集与启动对账。复测遥测仍写回原问题的 `runs/<fingerprint>.jsonl`，临时项目只承载隔离执行所需的数据库和夹具。

选择显式 purpose 标记而不是根据临时目录路径猜测，是因为后者脆弱且难以测试。备选的在临时 `opennovel.json` 中写禁用开关不符合当前「toolInsight 是全局设置」的约束。

### 4. 证据与信号在存储层去重

证据和负反馈信号追加都在对应锁内先读取现有稳定标识集合；发现相同 ID 时返回明确跳过结果，不重写 JSONL 行，也不再让问题文档重复摄取该条记录；无相同 ID 时先执行尾部撕裂修复再追加。这样即使多实例或多进程同时消费同一事件，锁会把并发串行化，第二个写入者会看到既有 ID 并放弃。

选择存储层去重而不是只依赖问题文档去重，是因为 JSONL 是客观证据和信号的原始 sink；文档层去重无法阻止同一文件出现重复行。备选的 SQLite 索引可以后续引入，但当前规模下 JSONL + 锁内读取已足够。

### 5. 负反馈用独立低噪声信号文件

新增 `signals.jsonl` 作为负反馈信号层，沿用追加写、尾部修复和锁纪律。记录包含稳定信号 ID、时间、目标范围、反馈类别、session/prompt message 引用和发生实例 ID。
目标范围固定为 `writing`、`tool`、`process`、`unknown`，反馈类别固定为 `result_rejected`、`tool_misuse`、`flow_issue`、`other`；信号类聚合键使用目标范围加反馈类别，不使用自由文本。
检测只订阅 `session.next.prompt.admitted`，用本地确定性规则识别明确负面评价；模糊表达不记录。检测过程不调用模型，也不把提示文本、完整对话、章节正文或文件附件写入信号层。
内部复测、归因会话和非用户提示不采集。

选择独立 JSONL 而不是直接写入 `evidence.jsonl`，是因为负反馈不总是工具失败证据，过早建 issue 会制造噪声。选择不保存文本摘要，而不是自动脱敏保存一段文本，是因为「不对 / 错了」的真实语境需要用户确认后才值得持久化。用户确认升级时，仍走现有 `tool_insight` 的 `feedback` 白名单和脱敏截断路径。

### 6. 负反馈信号与 issue 解耦

信号文件只负责计数和聚合；升级为 `user_report` 时由用户确认或显式记录入口触发。`tool_insight` 新增 `list_signals` 与 `upgrade_signal` 动作：前者只返回信号 ID、时间、稳定枚举和升级状态，后者接受一个或多个已确认信号 ID 和可选脱敏描述。升级时通过现有证据记录的白名单字段携带这些信号 ID，问题文档格式不变。
升级指纹由目标范围、反馈类别和可选已注册工具名等稳定事实派生，不使用原文；不同目标或类别的报告不强行合并，既有显式用户报告保持旧指纹兼容。
同一证据锁内先读取既有升级证据的信号 ID 集合，任一信号已升级即整体跳过；新的升级证据沿用所选信号的发生实例 ID，避免重复计数。
升级时可要求用户补充脱敏描述；信息不足时按既有规则标为未知，不编造根因。

选择「确认升级」而不是高频自动建档，是因为一次负反馈可能只是风格纠偏，重复出现也不必然代表工具缺陷。

## Risks / Trade-offs

- [会话归属缺失导致漏采] → 未观察到创建事件时优先查询持久会话归属；仅在其位置与当前插件装载位置一致时兜底，临时复测或仍无法确认的会话丢弃并保留诊断信息。
- [负反馈误报] → 信号层只记录稳定枚举和引用，不自动建 issue；升级必须经用户确认。
- [隐私压力] → 信号层不存原文；升级后的文档继续走既有脱敏、截断和正文授权规则。
- [旧目录残留] → 本次不自动清理历史空根，避免误删用户数据；后续可提供显式维护命令。
- [JSONL 长度增长] → 锁内读取去重成本随文件增长；如果后续成为瓶颈，再引入本地索引或 SQLite，不在本 change 提前扩展。

## Migration Plan

- 不迁移数据库，不改公开协议，不需要重新生成 SDK。
- 旧日志目录保留；新逻辑只影响新证据、新信号和新复测运行。
- 上线后空项目不再产生新空根；已有空根仍保留。若用户需要清理，可另行提供显式维护入口。
- 回滚时恢复原有启动初始化即可，已写入的新 `signals.jsonl` 保留为普通本地文件。
