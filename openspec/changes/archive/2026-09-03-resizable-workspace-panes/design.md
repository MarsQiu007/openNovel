# 设计：工作台分栏宽度可拖拽调节

## Context

`unify-novel-workspace-layout` 落地后的布局系统：左右栏固定宽（288/380），`ResizeObserver` 监听 Body 容器宽度做两档自动收边（<1100 收右栏、<1008 收左栏），`leftManual`/`railManual` 三态（null = 跟随规则，布尔 = 手动覆盖，宽度回阈值以上清 null），persist key `novel.workspace.layout.v1`。`packages/ui` 已有现成 `ResizeHandle` 组件（min/max clamp、`collapseThreshold` 拖到头收起、双击时 `mousedown` 以 `e.detail > 1` 早退可安全绑 `onDblClick`），本变更零新增 UI 组件。

关键既有事实：自动收边判定观察的是 Body 容器全宽（不扣左栏），因此 1100~1388 区间（三栏并存）主区实际低于 720——归档 spec"1100 = 右栏 + 720"的算术隐含"左栏不在场"，是措辞漏洞。本设计将保底语义明确为终态保证。

## Goals / Non-Goals

**Goals:**

- persist 只存用户意图（设定宽度），渲染即意图，不设第二份宽度状态
- 阈值全部从设定宽度派生，"主区保底 720"成为唯一硬编码常量
- 默认宽度下与归档实现行为逐比特一致（右档 1100 / 左档 1008），零回归

**Non-Goals:**

- 不做主区宽度调节、逐视图栏宽、栏宽快捷键（见 proposal Non-Goals）
- 不重构 ResizeObserver 的观察对象与回调结构（沿用 Body 容器观察，无反馈环）

## Decisions

### D1：宽度即设定值——不设第二份宽度状态

persist 存设定宽度，展开态渲染直接使用设定宽度：`生效宽度 = 设定宽度`（收起态不渲染）。不引入 clamp / 生效宽度层。

clamp（`生效 = min(W, 可用 - 720)`）在探索中被否决，理由有二：

1. **口径错误**：右档判定用 Body 全宽，clamp 的"可用"需扣左栏，两者相差 `W_l`——所谓"自动态零参与"不成立，clamp 会在 1100~1388 过渡区持续压制右栏（Body=1200 时压到 192），破坏"默认宽度下与归档行为逐比特一致"目标；
2. **与拖拽所见即所得冲突**：窗口不足时拖宽松手，栏会从拖拽值跳回 clamp 值。

删除 clamp 后主区保底仅承诺自动收边终态（D2 的证明与 clamp 无关）。手动展开与拖拽统一为用户主权：所见即所得，主区让路；用户可再拖窄或收起，窗口回阈值以上时手动会话结束、自动规则接管（自愈）。

备选：clamp 仅在 manual 态启用。拒绝——仍有跳变问题（拖拽松手回跳），且条件分支引入两套宽度语义。

### D2：阈值派生——max 公式保证"随行先让位"

```
左档 = W_l + 720
右档 = max(W_r + 720, W_l + 721)   // +1 保证严格大于，随行永远先收
```

当用户把右栏拖得比左栏窄（如 320 < 350）时，纯数值顺序会使左档 1070 > 右档 1040、导航栏先收，违背角色语义；max 公式以一行代价保住"随行区先让位"。默认值下退化为 1100/1008，与归档实现一致。

终态保证的证明（"Body 宽"一律指 Body 容器全宽，不扣左栏）：渐进缩窗下，右栏收起发生在 Body 跌破右档时，收起后 Body ∈ (左档, 右档]，主区 = Body − W_l ≥ 左档 − W_l = 720——下界由**下一档阈值**提供（左栏未收正是因为 Body 未跌破左档）；左栏收起后主区 = Body ≥ 当帧窗口宽。因此渐进缩窗的每次收边完成后主区 ≥ 720。**跳变例外**：窗口一步跨两档（如 snap 分屏把 1388 拖到 500）时双档同帧触发，主区 = 窗口宽本身可低于 720——窗口本身不足时保底物理不可能，spec 场景以"窗口不低于保底"为前提限定。三栏并存的过渡区间（Body ∈ (右档, 1388)）主区可低于 720，右栏按设定宽度全宽显示——与归档固定宽度行为一致（D1 无 clamp 的直接结果）；spec 措辞已收敛为"收边完成后"（终态保证）。过程保证需把右档抬到 `W_l + W_r + 720`（默认 1388 才收右栏），过于激进，拒绝。

### D3：ResizeHandle 接线与收起联动

- 左栏手柄：`direction="horizontal" edge="end"`（手柄在栏右缘，向右拖增宽）；右栏：`edge="start"`（栏左缘，向左拖增宽）
- 边界：左栏 `[220, 400]` 默认 288；右栏 `[320, 560]` 默认 380（静态边界，不随窗口动态化；数值走查可微调，不影响语义）
- `collapseThreshold` = 各自 min：拖过 min 再外拽 → `onCollapse` → 设 `manual = true`——用户显式意图，与 »/« 按钮通道等价，手动会话生命周期照旧；拖拽收起时设定宽度提交为 min 值（ResizeHandle 的 mousemove 末帧已把 clamp 值送入内存 signal，`onCollapse` 时写入 store，再展开显示 min 宽度）
- 双击手柄 → 设定宽度写 null → 回落默认值；`ResizeHandle` 的 `mousedown` 对 `e.detail > 1` 早退，不与拖拽冲突
- 收起态（`railCollapsed()`）栏整体隐藏，手柄随之消失，无需单独处理

### D4：拖拽期间仅内存态，松手提交持久化

`onResize` 高频回调只更新内存 signal；`mouseup`（松手）才写入 layout store 触发 persist——避免每 mousemove 同步写 localStorage 造成长任务毛刺（dev HUD 已观测到 LONG 任务告警，不冒此险）。双击重置与拖拽收起都是单次离散动作，直接写 store。

### D5：persist 扩展——v1 加字段不升版本

`WorkspaceLayout` 追加 `leftWidth: number | null`、`railWidth: number | null`（null = 未拖过 = 默认宽度）。读取用 `typeof x === "number" ? x : null` 宽容处理，旧数据（无此二字段）自然回落默认，零迁移；沿用 `=== true` 式宽容读取的既有先例，版本号保持 v1。

## Risks / Trade-offs

- [左栏内容（章节列表/大纲/设定）在 220px 下过挤] → 列表类组件弹性好，风险低；实施期走查三档宽度（220/288/400）
- [SessionPage 在 320px（右栏下限）下的可用性] → 归档 change 已在 380px 走查通过；320px 仅比已验证宽度窄 60px，实施期专项走查 prompt 输入区
- [拖拽与自动收边的交叠（拖右栏手柄可能使可用宽跌破左档）] → 阈值判定基于 Body 全宽（不随栏内分配变化），observer 不因拖拽触发，无交叠；实施期验证一次
- [拖宽设定值后进入悬置态（可用宽已低于新阈值但栏保持展开）] → observer 仅在 Body 宽变化时判定，悬置态在下次窗口宽度变化时被自动规则收编；拖拽中触发收起会中断交互，故接受
- [极窄窗口手动展开双侧栏可致主区趋零] → 需双重显式操作，且窗口回阈值以上自动规则即接管；接受（用户主权语义）
- [窄窗口手动展开按设定宽度显示会挤压主区] → 主区视图（阅读纸面等）弹性自适应；实施期走查窄窗口手动展开后的主区可用性
- [阈值上方手动收起（按钮或拖到头）后，窗口 below→above 往返会清除 manual 使栏自动弹开] → 归档 manual 三态的既有跨界语义（清 null 需一次穿越），非本提案引入；拖拽收起通道使其更易触发。不在本提案修（动主 spec 的手动收起语义，超出宽度拖拽范围），走查观察，若确需 sticky 收起另开提案修 manual 生命周期
