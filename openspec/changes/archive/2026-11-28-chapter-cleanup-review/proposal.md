# Proposal

## Why

导入整理队列的纠错阶段只产出建议清单（章节定位 + 原文/建议对照），以进度笔记与会话文本形态存在，队列终结后明细即丢失。用户看不到可操作的修订入口，错字、无用信息、冗余段落实际不会被修改——「整理了但什么都没发生」。需要把纠错产出升级为落库的修订提案实体：可逐条审阅、可批量接受低风险项、接受后确定性事务写入正文并留版本可回滚。

## What Changes

- **修订提案实体**：纠错阶段每条建议落库为章节修订提案，携带修订类型（错字替换 / 无用信息删除 / 重复段落删除 / 格式残留清理）、段落锚点、原文引用、建议文本、理由与置信度。
- **审阅面板**：设定树新增「清理修订」审阅面板，按书聚合待审提案，支持逐条接受/拒绝与批量接受低风险项；节点显示待审计数徽标；已应用项可撤销。
- **低风险批量接受**：错字替换与格式残留清理且置信度达阈值（0.9）的提案视为低风险，可一键批量接受；内容删除类（无用信息/重复段落）一律逐条人工审。
- **确定性事务应用**：接受后单事务完成「应用前正文快照 → 锚点原文校验 → 机械替换/删除 → 正文与字数更新 → 提案标记已应用」；锚点漂移的提案标记失败并说明原因，不阻断同批其余项。
- **撤销回滚**：已应用提案可撤销，恢复至应用前快照内容（追加新版本留痕，历史版本不删）。
- **汇总统计升级**：汇总汇报的纠错部分改为读修订提案库的实数（已应用 / 待审 / 拒绝 / 失败数量），取代纯文本建议罗列。
- **AI 不直改原则保留**：子代理只产出提案，永不直接修改正文；正文变更仅发生在用户接受触发的确定性应用中。

## Capabilities

### New Capabilities

- `chapter-cleanup-review`: 章节清理修订提案的落库、审阅、低风险批量接受、确定性事务应用、撤销回滚与统计汇总能力。

### Modified Capabilities

- `book-import-pipeline`: 纠错阶段产出形态从「建议记入产出与汇总文本」升级为「结构化修订提案落库」，替换既有「纠错建议禁止直改正文」需求的内容表述（AI 不直改的原则保留）。

## 非目标

- 不改变批注（annotations）体系：批注仍是创作过程审阅意见，执行走 AI 改稿；修订提案是导入清理的确定性纠错，两者语义与面板互不相通。
- 不做 AI 改稿式修订：接受即机械应用替换/删除，无创作成分；需要改写润色的场景仍走批注或章节审批流。
- 不改变导入管线（analyze/apply/兜底分章）与整理队列结构（单读三产出、单元组织、断点续跑）。
- 不做跨书批量、撤销链（多次撤销回溯多步）或提案过期回收（stale/retire）。
- 不调整既有正文写入路径（write_chapter / revise_chapter / 服务端编辑）的事务化缺口——那是独立的基础设施问题。

## Impact

- `packages/novel-store`：修订提案新表（含索引）与幂等迁移；提案 CRUD 与「快照+替换+标记」事务化应用助手、撤销助手。
- `packages/plugin`：新增 `propose_cleanup` 工具（纠错阶段落库入口）；director 导入整理指令中纠错阶段的产出要求更新。
- `packages/schema` / `packages/protocol` / `packages/server`：修订提案的契约 schema、HttpApi 端点（列表/计数/接受/批量接受/拒绝/撤销）与 handler；新端点同 PR 注册 httpapi-exercise 场景。
- `packages/client`：`bun run generate` 再生成 SDK，同步 codemode fixture。
- `packages/app`：清理修订审阅面板（挂设定树 organization 节点 + 待审徽标）；文案进既有 locale 体系（zh/en/zht）。
- `packages/desktop`：无直接改动（随 app 与后端发版）。
- 数据兼容性：纯新增表与迁移，不动既有表；旧提案无历史数据；既有批注、章节版本、审批流行为不变。
