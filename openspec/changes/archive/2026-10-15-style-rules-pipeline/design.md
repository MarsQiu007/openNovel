# Design

## Context

风格规则链路现状（实证与动机见 proposal.md 的 Why）：

- 写入：设定保存工具的 style_guide 分支把 rules 交给只保留顶层标量的归一化（嵌套值直接跳过），非空规则被吞成 `{}` 后仍走成功计数路径；状态提交管线的 style 分支复用同一函数；书籍元数据联合保存则直接 JSON.stringify rules（json 列上形成双重编码）。
- 读取：服务端有各自的容错归一化（数组按冒号拆分、嵌套丢弃），与写入侧不一致；UI 面板按 `键: 值` 行序列化展示；内嵌阅读器风格页直接渲染原始行（历史嵌套形态显示 [object Object]）。
- 消费：写作快照只渲染基调、视角、时态；`chapter_length` / `chapter_length_limit` 被单独解析为目标字数与篇幅开关；预算层按 `JSON.stringify(rules)` 估算 token，但超 1K 时把整个风格指南置空——大规则集的书连基调、视角、时态都进不了快照。

## Goals / Non-Goals

**Goals：**

- 归一化成为单一事实源，写读两侧同构；嵌套、数组、文本形态全部可解析，无法解析的写入响亮失败。
- 快照让 writer 看见规则，且大规则集不再导致整个风格段消失。

**Non-Goals：**

- 不引入嵌套存储或树形编辑（扁平字符串映射是唯一规范形态）。
- 不做数据迁移与自动回填；不改 tone/pov/tense 语义与 chapter_length 特殊键的消费逻辑。
- 不改 HTTP 契约，无 SDK 再生成。

## Decisions

### D1: 归一化函数落在 novel-store，作为唯一事实源

签名（示意）：`normalizeStyleRules(rules: unknown): { rules: Record<string, string>; unnormalizable: boolean }`。

备选：a) plugin 内部实现、server 复制一份——两份逻辑必然漂移（现状即如此）；b) 放 plugin 让 server 依赖——违反依赖方向（server 不依赖 plugin）。novel-store 已被 plugin（session-store shim）与 server 共同依赖，且其定位就是小说内容的规范数据层。

调用点：plugin 写入路径（设定保存工具、状态提交管线）与读取路径（设定检查工具）、server 读取路径（风格指南读取归一化）、novel-store 自身写入边界（风格指南 upsert、书籍元数据联合保存 saveBookMeta）、内嵌阅读器读取路径（opennovel 风格接口）。

### D2: 展平语义

- 键连接符 `.`（如 `异能体系.等级严格`）；数组索引 `0`、`1`…（嵌套路径下为 `父.0`）。
- 叶子值：字符串保持；数字与布尔 `String()`；null、undefined 与空容器不产生条目。
- 字符串输入两级解析：JSON → 失败再按行 `键: 值`；行文本要求每个非空行可解析，否则整体拒绝——部分丢弃正是本次要消灭的模式。
- `unnormalizable` 仅当输入非空（有键、有元素、非空串）且产出 0 条目；顶层显式空对象、空数组、空串视为“清空”，不报错。
- 不做逆解析（不把 `父.子` 键还原成嵌套），避免歧义。

### D3: 失败语义按调用方分层

- 设定保存工具：按条收集错误，跳过该条全部字段写入（tone/pov/tense 也不写），工具输出带格式建议。
- 状态提交管线：归一化失败抛错、事务回滚（该次提交整体失败），由管线报告明确错误。
- 服务端读取：只读场景不做失败处理——unnormalizable 的遗留数据以空映射展示（无写操作，不会丢数据）。
- novel-store 写入边界（upsertStyleGuide / saveBookMeta）：归一化失败时抛错（saveBookMeta 位于主事务内，抛出即整体回滚），与状态提交管线一致，不静默降级。

### D4: 快照渲染所有规则条目

快照工具输出与会话级系统注入的风格段统一追加规则行（`- 键: 值`），渲染对象是预算裁剪后的映射；`chapter_length` / `chapter_length_limit` 等特殊键照常渲染（透明度优先），其既有的目标字数与篇幅开关消费逻辑不变。

### D5: 风格指南预算改为“固定部分优先 + 规则逐条截断”

P4（1K tokens）内：先保留基调、视角、时态（不再因规则超量整体置空）；剩余额度按插入顺序容纳整条规则，发生截断时在快照数据上携带截断标记，渲染层追加提示行（含设定检查工具引导）；题材规则使用其余额度（风格优先于题材规则的既有次序不变）。

备选：维持“超预算整体丢弃”——放弃；D 的目标是大规则集可见，且现状对大规则集等于丢失整个风格段。

### D6: 契约与生成物

读取与写入仍是 `Record<string, string>`，HTTP 协议形状与 SDK 生成物不变，无需在 packages/client 再生成。

## Risks / Trade-offs

- [行文本严格解析拒绝含杂行的清单] → 错误信息回显首个无法解析的行与格式要求，agent 可据此修正重试。
- [`父.子` 连接与既有含点键可能冲突] → 扁平映射为唯一规范形态，不做逆解析；含点键按原样保留。
- [历史数组数据展示由“按冒号拆分”改为“索引编号”] → 内容不丢、可回存；属展示变化，兼容性已在 proposal 说明。
- [规则渲染挤占 P4、题材规则可用额度变小] → 两者同层竞争为既有设计；截断提示可引导按需查询完整规则。
- [状态提交遇到病态 rules 时整次提交失败] → 归一化已覆盖现实输入形态（嵌套、数组、文本），失败仅剩病态输入；明确失败优于静默丢数据。
- [书籍元数据联合保存纳入归一化后，病态输入从写入怪异数据变为整体拒绝] → 与全局写契约一致，事务回滚保证原子性；正常扁平输入行为不变。

## Migration Plan

无 schema 变更、无数据迁移：发布即对新写入与读取生效。历史丢失数据（如《执棋人》的 `rules={}`）不在代码自动恢复范围，可从会话日志人工回填（独立操作，另行安排）。回滚：还原代码即可；新写入形态是旧形态的严格超集（展平扩展），无不可逆数据变化。
