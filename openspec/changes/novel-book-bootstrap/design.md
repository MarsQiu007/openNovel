# 设计：新书 AI 初始化衔接

## Context

向导完成后只是书籍壳记录，`init_novel` 的完整开书流程主要服务于全局会话；书内空会话当前只建议“写下一章”。`write_chapter` 会校验待统改任务、字数、大纲标签和重复度，但不感知“零角色 + 零世界观”的新书状态。

## Goals / Non-Goals

**Goals**

- 在书内空会话给出可见、低摩擦、用户主动触发的初始化入口。
- 让初始化提示词携带足够上下文，避免 director 把请求误判为普通写作。
- 阻止完全无设定的第一章静默落库。
- 保持旧书、已有内容和已有最小设定项目的写作路径可用。

**Non-Goals**

- 不在向导完成后自动调用模型或静默派发 `@architect`。
- 不改变 `setup_mode` 或 `writing_mode` 的语义。
- 不新增数据库迁移或初始化完成标记表。
- 不把提示词包装逻辑散落到多个 UI 入口。

## Decisions

### Decision 1: 用空会话建议承载显式入口

向导完成后仍进入书内工作台；当空会话、零角色、零世界观同时成立时，把“初始化小说设定”作为第一个建议 chip，原来的“写下一章”仅在已有核心设定后显示。用户点击才创建并绑定会话，不自动派发任务。

**替代方案**：向导提交后自动派发初始化。这会消耗模型调用、增加失败路径，并且在用户只想先查看书页时造成打扰，因此放弃。

### Decision 2: 由书内空会话组装初始化提示词

初始化 chip 使用当前书籍详情组装一条明确的提示：请求初始化小说设定，并包含书名、类型、简介。`createAndBindSession` 仍只负责“建会话、绑定、发首条消息”，不新增会话专用 API。

这样利用 director 现有路由：初始化请求会进入 `@architect` 流程；UI 不直接依赖 plugin 工具内部实现。

### Decision 3: 用角色与世界观条目判断零设定

核心设定存在性复用工作台已有的角色和世界观查询：两者都加载完成且数量为 0 时认为处于零设定状态。查询加载中不显示初始化 chip，避免在数据尚未返回时误导用户。

不新增“初始化完成”标记。这个定义可能比完整故事圣经更宽松，但足以识别完全裸书，且避免引入 schema 变更和历史数据迁移。

### Decision 4: 只对真正裸写的首章硬防护

`write_chapter` 在满足以下全部条件时拒绝写入：目标章是第一章、当前正文为空、小说无角色且无世界观条目。返回信息说明“请先初始化小说设定”，并让模型把初始化作为下一步。

只要已有任一核心设定、章节已有正文、或章节序号不是 1，就不拦截。这样旧书回写、修订和非首章生成不会被误伤。

## Risks / Trade-offs

- [用户只想手写第一章] → 需要先保存至少一条角色或世界观设定；这比静默裸写更符合新书旅程。
- [核心设定数量为 0 不代表一定未初始化] → 只影响 UI 建议和首章防护，不修改配置语义；已有正文或非首章不受影响。
- [初始化模型调用可能失败] → 用户主动触发时沿用现有会话创建错误提示，输入不自动重试。
- [书名/类型/简介来自向导数据] → 使用现有书籍详情，不新增提示词配置。

## Migration Plan

1. 在书内空会话加入零设定状态判断与初始化 chip。
2. 组装并提交包含书籍上下文的初始化提示词。
3. 在 `write_chapter` 增加首章零设定拒绝分支。
4. 用组件/工具测试覆盖零设定、已有设定、已有正文和非首章场景。
5. 运行 `packages/app` 与 `packages/plugin` typecheck、相关测试和全仓验证。

回滚方式是 revert 对应提交；无数据迁移。
