## Context

当前写作快照先装配全量角色和关系，再按章纲/活跃角色筛选世界观，并对关系做普通 P5 截断。writer 提示词把 `worldEntries` 标为最高优先级，但角色关系只作为普通列表输出，格式通常是 `角色A ↔ 角色B（类型）`。这导致关键亲属关系可能丢失或方向不清。

## Goals / Non-Goals

**Goals:**

- 建立一个“受保护关系上下文”层，不依赖普通 P5 截断顺序。
- 关系选择同时覆盖双方都相关和只有一方相关的情况。
- 在快照文本中输出方向化关系和关系派生的亲属称谓绑定。
- 超出保护容量时给出明确裁剪警告。

**Non-Goals:**

- 不迁移或扩展数据库 schema。
- 不引入通用角色别名表、向量检索或全局实体链接系统。
- 不在本次处理 auditor、observer 和候选区行为。

## Decisions

### 1. 在快照内增加受保护关系层

在上下文装配结果中区分：

- 普通关系列表：维持现有筛选和截断行为。
- 受保护关系：与章纲、活跃角色或最近章节直接相关的正式关系。

受保护关系先经过排序，再进入专用硬约束段落。排序优先级为：

1. 双方都是活跃角色。
2. 只有一方是活跃角色，但关系能解释其身份。
3. 章纲或最近章节摘要明确出现角色名或关系关键词。

备选方案是直接把所有关系放入硬约束区。这个方案更简单，但长篇小说中会造成上下文膨胀，因此不采用。

### 2. 为关系保留专用预算

在现有 P5 预算内划出关系保护预算，并先写入受保护关系，再分配给世界观全文、导览和卷纲。保护预算应能覆盖常见单章关系集合，但不承诺无限关系都完整保留。

当受保护关系超过专用预算时：

- 按上述优先级保留最高优先级关系。
- 在快照工具输出和 metadata 中加入可观察的 `relationship_context_truncated` 状态。
- pipeline 可以据此提示人工或让下一轮上下文更聚焦。

### 3. 用确定性规则解析关系方向

新增关系方向渲染逻辑，仅使用关系表已有字段，不新增数据库列：

- 优先从 `description` 中识别“角色名 + 母亲/父亲/儿子/女儿”等明确表述。
- 其次按中文复合关系类型的约定顺序解析，例如 `母子`、`父子`、`母女`、`父女`。
- 无法判断方向时保留原始 `类型 + 描述`，并显式标记方向未解析，不虚构父子/母子哪一方。

备选方案是要求用户改造数据模型，为关系增加显式 `direction` 字段。虽然长期更严谨，但会带来数据迁移和 UI/API 改动，不符合本次小步修复目标。

### 4. 从关系派生保守亲属称谓

只为既有命名角色生成关系派生称谓，例如：

- `张三是李四的儿子`
- `称谓“儿子”绑定到张三`
- `称谓“母亲”绑定到李四`

不引入通用角色别名表，也不把普通昵称、代词、泛称自动加入别名映射。存在多个可能匹配对象时保留为未解析，不强行绑定。

## Risks / Trade-offs

- [中文关系类型表述多样，方向解析可能失败] → 无法解析时保留原始描述并显式标记方向未解析，后续防漂移提案继续审计。
- [保护关系会挤压世界观全文] → 只保护与本章相关的关系，并让非核心世界观优先降级。
- [快照文本变长] → 使用专用预算和优先级排序，避免无界增长。
- [关系描述本身错误会变得更权威] → 本提案只负责忠实呈现；修正入口和审计兜底由 `writing-drift-guards` 处理。

## Migration Plan

- 纯运行时上下文行为变化，无数据库迁移。
- 旧数据缺少方向或描述时继续以原始类型显示，并标记方向未解析。
- 回滚方式是移除受保护关系段落和专用预算逻辑，恢复现有 P5 截断顺序。
