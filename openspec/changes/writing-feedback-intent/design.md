## Context

写作反馈有多个进入点：初次生成通过 pipeline 派发 `writer`；用户说“修一下第 X 章”时，director 会先派发 `auditor`，再可能派发 `reviser`；驳回后重写通过 pipeline 把旧章节和用户批注交给 `reviser`。当前 `writer` 与 `reviser` 的提示词只说明“精准修正”和风格保持，没有要求先区分“用户纠正语言”和“小说叙事事实”。因此模型容易把“不会心情低落”当成一句可以放进正文的事实，而不是删除“心情很低落”的编辑动作。

本方案不引入数据库迁移或公开 API 变更，只在写作链路的输入、提示词与验证层建立统一协议。

## Goals / Non-Goals

**Goals:**

- 在 director 或 pipeline 派发 writer / reviser 前，把用户反馈整理成统一的结构化反馈意图。
- 保持初次生成、director 直接修订和驳回后重写使用同一套“控制层 → 故事层”转换规则。
- 让 writer / reviser 明确处理纠正型否定、剧情事实、风格约束和模糊反馈。
- 让 auditor 对照反馈意图区分控制层泄漏与合法剧情否定。
- 增加可测试的提示词约束和关键场景用例。

**Non-Goals:**

- 不新增独立反馈解释 agent，也不增加第九个流水线步骤。
- 不把反馈意图持久化为新的数据库实体。
- 不改动审批、章节版本、设定影响面或公开 API 契约。
- 不做全量语义解析；复杂或歧义反馈仍需用户澄清。

## Decisions

### 1. 由派发方统一编译反馈意图

反馈编译协议由 director 和 pipeline 共同遵守：谁要派发生成或修订执行者，谁负责先编译反馈意图。

- 初次生成：pipeline 在派发 `writer` 前编译。
- 驳回后重写：pipeline 基于旧章节和原始批注编译，再派发 `reviser`。
- director 直接修订：director 先编译，再按现有流程派发 `auditor` 和 `reviser`。

这样可以避免为每个执行者重复解释原始反馈。独立反馈解释 agent 会增加延迟和一次模型调用，而现有调度方已经有任务、章节和用户反馈上下文；当前规模下收益不足。

### 2. 原始反馈与任务摘要分开传递

调度方可以补充任务范围、章节 ID 或上下文摘要，但必须保留用户原始反馈。反馈编译以原始反馈为准，避免 director 的转述提前改变语义：

```text
【用户反馈原文】
现在主角不会心情低落

【任务范围】
修订第 3 章；保持主线事件不变
```

### 3. 使用结构化文本块作为执行者输入

反馈意图使用稳定的中文结构化文本块，而不是新增 API 字段：

```text
【写作反馈意图（控制层，禁止写入正文）】
- 反馈编号：F1
- 意图类型：remove_assertion / replace_assertion / constrain_future / narrative_fact / unclear
- 目标引用：心情很低落
- 禁止断言：主角心情很低落
- 期望状态：主角平静或无情绪突出地进入场景
- 保留内容：来到地点；完成当前动作
- 允许正文否定：false
- 原始反馈：现在主角不会心情低落
- 澄清问题：无
```

一次反馈包含多条可执行意图时，按反馈编号逐条列出。文本块便于现有 agent prompt 和流水线 dispatch prompt 复用，也便于测试断言关键字段。若未来需要 UI 展示或 API 返回，再把它升级为协议类型；本提案先不扩展公开契约。

### 4. 定义默认转换规则

| 用户反馈形态 | 默认意图 | 执行规则 |
|---|---|---|
| “不要 X”“不再 X”“现在不会 X” | remove_assertion | 从正文删除或替换 X；禁止新增“不会 X”“没有 X”的解释性复述 |
| “把 X 改成 Y” | replace_assertion | 用符合叙事语境的 Y 替换 X；保留无关情节 |
| “以后不要 X” | constrain_future | 只约束后续生成，不为了当前章制造否定说明 |
| “他没有带伞”且语境是剧情事实 | narrative_fact | 可按叙事语气写否定句，但不添加作者说明 |
| 无法确定是约束、事实还是修改目标 | unclear | 只对该条停止执行并返回具体澄清问题 |

“允许正文否定”必须显式出现在意图中。纠正型否定默认为 `false`；明确剧情事实或用户明确要求时可设为 `true`。多条反馈中有模糊项时，不丢失其他明确意图；但依赖或冲突于模糊项的意图必须等待澄清后才执行，避免生成局部不一致的正文。

### 5. writer 与 reviser 使用同一故事层协议

两个执行者都增加以下硬规则：

- 先读取结构化反馈意图，不把原始反馈当作叙事材料。
- 纠正型否定只能导致删除、替换、场景重写或后续约束。
- 只有 `narrative_fact` 且用户明确给出剧情事实时，才允许正文否定句。
- 修改旧章节时先根据目标引用定位受影响断言，再做最小改动，并检查相邻句子的语法与节奏。
- 意图为 `unclear` 时返回澄清请求，不得猜测生成。

### 6. auditor 对照意图检查控制层泄漏

auditor 增加一个检查点：识别章节中因遵守用户反馈而产生的元说明、作者解释、直接复述用户原话或与反馈语义相反的否定句。pipeline 或 director 在派发 auditor 时必须附带反馈意图摘要；没有意图时，auditor 报告缺少反馈上下文，不得机械否定所有正文否定句。该检查不新增数据库表，不改变 37 维审计的对外命名；发现问题时进入现有 revise 流程。

### 7. 测试策略

- 用 agent prompt 测试断言 writer / reviser 包含结构化反馈协议和否定转换规则。
- 用 pipeline prompt 测试初次生成和驳回重写都会先构造反馈意图。
- 用 director prompt 测试直接修订会保留用户原话、先编译意图，并把意图摘要传给 auditor。
- 用固定夹具验证示例输出：旧句“心情很低落”被移除，且“心情不会很低落”不进入正文。
- 用澄清场景验证 `unclear` 不自动派发修改。
- 保留现有插件全量测试，确保没有破坏审批和修订工具行为。

## Risks / Trade-offs

- [中文否定和隐含指代解析仍可能出错] → 用结构化意图、审计检查和模糊反馈澄清兜底；不追求全自动理解。
- [结构化文本块增加 dispatch prompt 长度] → 只在有用户反馈时注入；字段保持短句，多条反馈按编号拆分。
- [审计可能把合法剧情否定误判为控制层泄漏] → 要求意图块显式提供 `narrative_fact` 与 `允许正文否定`，审计优先对照意图而非机械匹配否定词。
- [调度方转述可能改变用户语义] → 强制保留原始反馈并以原话为编译依据。
- [pipeline 编译反馈本质仍依赖模型] → 通过固定字段、示例测试和 auditor 复查降低漏检率；若后续仍不稳定，再考虑独立解释器或确定性校验工具。

## Migration Plan

1. 先新增统一协议和 agent 提示词，不改变数据结构。
2. 更新初次生成、director 直接修订与驳回后重写的 dispatch 规则。
3. 补充 prompt 与关键行为测试。
4. 现有章节无需迁移；旧会话中的原始反馈继续按普通文本传给调度方，由新协议在派发前解释。

回滚只需恢复相关提示词与测试，不涉及数据回滚。
