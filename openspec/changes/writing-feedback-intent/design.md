## Context

`pipeline` 目前会把原始用户批注随旧章节一起传给 `reviser`，初次生成时也会把用户要求并入 `writer` 的任务输入。`writer` 与 `reviser` 的提示词只说明“精准修正”和风格保持，没有要求先区分“用户纠正语言”和“小说叙事事实”。因此模型容易把“不会心情低落”当成一句可以放进正文的事实，而不是删除“心情很低落”的编辑动作。

本方案不引入数据库迁移或公开 API 变更，只在写作链路的输入、提示词与验证层建立统一协议。

## Goals / Non-Goals

**Goals:**

- 在 pipeline 派发 writer 或 reviser 前，把用户反馈整理成统一的结构化反馈意图。
- 保持初次生成、普通修订和驳回后重写使用同一套“控制层 → 故事层”转换规则。
- 让 writer / reviser 明确处理纠正型否定、剧情事实、风格约束和模糊反馈。
- 增加可测试的提示词约束和关键场景用例。

**Non-Goals:**

- 不新增独立反馈解释 agent，也不增加第九个流水线步骤。
- 不把反馈意图持久化为新的数据库实体。
- 不改动审批、章节版本、设定影响面或公开 API 契约。
- 不做全量语义解析；复杂或歧义反馈仍需用户澄清。

## Decisions

### 1. 由 pipeline 统一编译反馈意图

选择在 pipeline 派发 writer / reviser 前完成反馈编译，而不是让 writer 和 reviser 各自理解原始反馈。

pipeline 已经掌握任务目标、上下文快照、目标章节和驳回批注，最适合把用户语言转成带操作语义的结构化意图。writer 与 reviser 继续专注故事层生成。

替代方案是为反馈新增独立 agent。它可以强化职责隔离，但会增加延迟和一次模型调用，而且 pipeline 本身已经具备任务编排上下文；当前规模下收益不足。

### 2. 使用结构化文本块作为执行者输入

反馈意图使用稳定的中文结构化文本块，而不是新增 API 字段：

```text
【写作反馈意图（控制层，禁止写入正文）】
- 意图类型：remove_assertion / replace_assertion / constrain_future / narrative_fact / unclear
- 禁止断言：主角心情很低落
- 期望状态：主角平静或无情绪突出地进入场景
- 保留内容：来到地点；完成当前动作
- 允许正文否定：false
- 原始反馈：现在主角不会心情低落
- 澄清问题：无
```

文本块便于现有 agent prompt 和流水线 dispatch prompt 复用，也便于测试断言关键字段。若未来需要 UI 展示或 API 返回，再把它升级为协议类型；本提案先不扩展公开契约。

### 3. 定义默认转换规则

| 用户反馈形态 | 默认意图 | 执行规则 |
|---|---|---|
| “不要 X”“不再 X”“现在不会 X” | remove_assertion | 从正文删除或替换 X；禁止新增“不会 X”“没有 X”的解释性复述 |
| “把 X 改成 Y” | replace_assertion | 用符合叙事语境的 Y 替换 X；保留无关情节 |
| “以后不要 X” | constrain_future | 只约束后续生成，不为了当前章制造否定说明 |
| “他没有带伞”且语境是剧情事实 | narrative_fact | 可按叙事语气写否定句，但不添加作者说明 |
| 无法确定是约束、事实还是修改目标 | unclear | 停止派发生成或修订，返回具体澄清问题 |

“允许正文否定”必须显式出现在意图中。纠正型否定默认为 `false`；明确剧情事实或用户明确要求时可设为 `true`。

### 4. writer 与 reviser 使用同一故事层协议

两个执行者都增加以下硬规则：

- 先读取结构化反馈意图，不把原始反馈当作叙事材料。
- 纠正型否定只能导致删除、替换、场景重写或后续约束。
- 只有 `narrative_fact` 且用户明确给出剧情事实时，才允许正文否定句。
- 修改旧章节时先定位受影响断言，再做最小改动，并检查相邻句子的语法与节奏。
- 意图为 `unclear` 时返回澄清请求，不得猜测生成。

### 5. 审计层检查控制层泄漏

auditor 增加一个检查点：识别章节中因遵守用户反馈而产生的元说明、作者解释、直接复述用户原话或与反馈语义相反的否定句。该检查不新增数据库表，不改变 37 维审计的对外命名；发现问题时进入现有 revise 流程。

### 6. 测试策略

- 用 agent prompt 测试断言 writer / reviser 包含结构化反馈协议和否定转换规则。
- 用 pipeline prompt 测试初次生成和驳回重写都会先构造反馈意图。
- 用固定夹具验证示例输出：旧句“心情很低落”被移除，且“心情不会很低落”不进入正文。
- 用澄清场景验证 `unclear` 不自动派发修改。
- 保留现有插件全量测试，确保没有破坏审批和修订工具行为。

## Risks / Trade-offs

- [中文否定和隐含指代解析仍可能出错] → 用结构化意图、审计检查和模糊反馈澄清兜底；不追求全自动理解。
- [结构化文本块增加 dispatch prompt 长度] → 只在有用户反馈时注入；字段保持短句和数量上限。
- [审计可能把合法剧情否定误判为控制层泄漏] → 要求意图块显式提供 `narrative_fact` 与 `allow_narrative_negation`，审计优先对照意图而非机械匹配否定词。
- [pipeline 编译反馈本质仍依赖模型] → 通过固定字段、示例测试和 auditor 复查降低漏检率；若后续仍不稳定，再考虑独立解释器或确定性校验工具。

## Migration Plan

1. 先新增统一协议和 agent 提示词，不改变数据结构。
2. 更新初次生成与驳回重写的 pipeline dispatch 规则。
3. 补充 prompt 与关键行为测试。
4. 现有章节无需迁移；旧会话中的原始反馈继续按普通文本传给 pipeline，由新协议在派发前解释。

回滚只需恢复相关提示词与测试，不涉及数据回滚。
