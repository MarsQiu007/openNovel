## Why

AI 常把用户的纠正性反馈当成正文内容复述，例如用户说“主角不会心情低落”，AI 却改写成“主角的心情不会很低落”。初次生成、director 直接修订和驳回后重写都会出现该问题，说明反馈进入 writer / reviser 前缺少统一的故事层与控制层隔离。

## What Changes

- 新增统一的写作反馈解释协议，把用户反馈先解释为结构化写作意图，再交给生成或修订流程。
- 覆盖初次生成、director 直接修订和驳回后重写三类路径。
- 区分纠正型否定、剧情事实、风格约束和模糊反馈；纠正型否定默认表示删除或替换叙事断言，而不是在正文里写出否定句。
- 支持一次反馈包含多条意图，并保留每条意图的目标引用、期望状态和需要保留的内容。
- `writer` 和 `reviser` 只消费结构化反馈意图；原始用户反馈仅作为追溯上下文，不直接作为叙事材料。
- auditor 根据反馈意图区分控制层泄漏和合法剧情否定。
- 增加提示词与关键路径测试，验证“不要 X / 不会 X”不会变成“不会 X”的正文复述。

### 非目标

- 不构建通用自然语言理解引擎，也不保证识别所有隐含指代。
- 不改变章节版本、审批、候选区或设定影响面的数据模型。
- 不新增云端服务、独立反馈解释 agent 或 UI 编辑器。
- 不禁止小说正文中合法的否定句；只限制把用户纠正语言直接翻译进正文。

## Capabilities

### New Capabilities

- `writing-feedback-intent`: 定义用户写作反馈如何转换为结构化生成或修订意图，并约束 writer / reviser 的故事层输出与 auditor 的意图感知检查。

### Modified Capabilities

- 无。

## Impact

- `packages/plugin`：更新 director / pipeline / writer / reviser / auditor 的输入协议与提示词，新增相关测试；不修改公开 HTTP API。
- `packages/app` / `packages/desktop`：无界面改动；现有会话和审批流可继续传入自然语言反馈。
- `packages/novel-store`：预计无 schema 或迁移改动。
- 本地数据兼容：现有章节、批注、驳回原因和会话历史继续可读；本变更只改变反馈在写作链路中的解释方式。
