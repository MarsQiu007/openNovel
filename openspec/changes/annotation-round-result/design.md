## Context

执行轮次的建表、创建、列表、更新接口和前端历史面板已经存在。当前缺的不是新端点，而是“AI 可用、可校验、可追溯”的结果回填通道：指令缺少轮次 ID，前端把发送成功误当作执行完成，更新契约也没有章节版本关联。plugin 内的格式化副本仅被测试使用，真实前端使用独立的纯逻辑实现。

## Goals / Non-Goals

**Goals:**
- 给 AI 一个明确、可校验的结果回填入口，并让指令稳定携带轮次 ID。
- 将“发送成功”和“AI 执行完成”两个阶段分开。
- 记录该轮执行对应的最新章节版本，避免历史面板只有一句摘要。
- 统一执行指令格式来源，删除 plugin 中的死代码副本。

**Non-Goals:**
- 不新增服务端执行调度端点；会话路由仍由前端负责。
- 不实现正文 diff、跨章批量执行和轮次统计。
- 不修改批注状态机或重新激活规则。

## Decisions

### D1: 复用更新接口，新增 plugin 工具作为 AI 入口
服务端已有 `PUT execution-rounds/:roundID`，本轮不新增重复 report 端点。前端继续使用该接口维护发送失败状态；AI 侧通过新的 `report_annotation_execution` 工具写入结果，工具调用本地数据层并做存在性校验。

**理由**：AI 工具运行在本地插件上下文中，可直接且安全地访问数据层；HTTP 更新接口继续服务于前端状态同步。重复新增“report”HTTP 端点只会让前端和 AI 有两条等价路径。

### D2: 指令携带轮次 ID 并要求完成后回填
前端生成指令时，把 `execution_round_id` 放入目标章节块，并在回填规则中说明：AI 完成或失败后必须调用 `report_annotation_execution`，不要只输出自然语言总结。

**理由**：这是结果归属的最小契约。不依赖会话消息查询、时间戳猜测或上下文反推。

### D3: 使用章节版本 ID 记录关联
在 `annotation_execution_rounds` 增加 `chapter_version_id` 可空列。AI 回填成功时，工具查询该章节最新版本并写入 ID；无法找到版本时允许为空，但结果摘要仍必须写入。

**理由**：版本 ID 比把版本号拼进摘要更结构化，也比为结果单独建表更轻。旧轮次该列自然为空，历史展示按可选数据处理。

**替代方案**：在摘要文本中拼“版本 N”。拒绝原因：展示层需要解析自然语言，格式漂移后无法可靠定位版本。

### D4: 发送成功后保持 running
前端不再在 `sendPrompt` 成功后调用完成更新。只有 AI 回填把状态改为 `completed` / `failed`。发送失败和批注关联失败仍立即标记为 `failed`。

**理由**：`completed` 语义应表示“AI 执行结果已知”，而不是“指令已发出”。这能自然驱动历史面板显示等待回填。

### D5: 前端纯逻辑作为指令单一来源
保留 `packages/app` 的批注执行纯逻辑，删除 plugin 中未使用的格式化函数和对应测试。plugin 工具只负责回填。

**理由**：前端已经掌握章节段落、标题、会话路由和轮次创建上下文，由它构造指令最直接；plugin 里的副本没有运行时价值。

## Risks / Trade-offs

- [AI 忘记回填] → 指令明确要求调用工具；历史面板保留 `running` 可见性，用户可重新发起或人工处理。
- [会话中断] → 本轮不自动判定中断；没有回填的轮次保持 `running`，历史展示为“等待回填”，避免误把中断标成失败。
- [最新版本可能不是本轮结果] → 工具在 AI 回填成功时取最新版本，仅作近似关联；后续如需精确 diff，可由改稿工具显式返回版本 ID 后增强。
- [旧数据库缺列] → 使用现有 `PRAGMA table_info` + `ALTER TABLE ADD COLUMN` 迁移模式，新库直接建新列。

## Migration Plan

1. `novel-store` 的 `CREATE_TABLES_SQL` 新增 `chapter_version_id`，旧库由迁移补列。
2. schema / protocol 扩展轮次输出与更新输入，并在 `packages/client` 重新生成 SDK。
3. plugin 增加回填工具并更新指令规则，随后删除重复格式化副本。
4. app 改成发送成功后保持 running，并扩展历史展示。
5. 回滚：新列可空，前端和历史展示兼容空值；隐藏回填工具后旧流程仍可查询和发送轮次。
