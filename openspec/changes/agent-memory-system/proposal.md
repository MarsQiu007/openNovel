# Proposal: agent-memory-system

## Why

长篇小说创作的核心痛点是**跨章一致性**：第 1 章确定的设定（角色外貌、世界观规则、伏笔承诺），到第 47 章时早已离开上下文窗口，起草 agent 无从参考，只能靠 37 维审计事后发现——发现时修订成本已经很高。上游 openCode 没有任何持久记忆机制（每次会话从零开始）；OpenHands 验证过一种可用的形态：**小而精的索引层（每次注入）+ 按需检索的档案层**。fork 已有 novel-store 数据层（角色、关系、世界观、伏笔表）和 FTS5 全文检索，是现成的地基，缺的是把"写作中沉淀的事实"变成"写作时可引用的记忆"这条链路。

经五轮设计讨论（存储形态、生命周期、来源扩展、冲突裁决、召回与整理、外部参照 Hindsight），方案已收敛，详见 design.md。

## What Changes

### 存储骨架（方案 C：结构化本体 + 派生注入层）

- **单一数据世界**：全部记忆存 novel-store（SQLite + FTS5），无向量库、无文件档案、无外部记忆服务
- **既有本体表不动**：角色表、世界观表、伏笔表是各自事实的唯一本体（伏笔表即伏笔记忆，不建平行伏笔卡）
- **新增自由事实表**：不属于既有实体的长尾设定（`book_id`、`source_chapter`、原文引句、`confidence`、`proof_count`、状态）
- **注入层是派生视图**：事实卡不是独立存储，由组装器从本体表现算；章审批通过时预计算下一章的注入包（物化视图，起草时一次数据库读）
- **横切状态层**：`pending → reviewed → approved → stale → retired` 生命周期状态机覆盖所有记忆来源，不每类实体各造一遍

### 记忆来源（两源 + 技巧第三源）

1. **正文事实**：起草时即时登记（pending，当章生效降权注入）→ 审计校准（reviewed，出处核实）→ 审批通过（approved）→ 正文修改触发 diff 范围重校准（stale→重提取 / retired 留痕）。触发器挂**文本变更事件**（状态提交、编辑器保存），覆盖 agent 修订与作者手改两条路
2. **设定引用**：不复制设定本体，引用既有表条目并附加 `planned/established` 落文状态 + 滞留提醒（planned 过久提示作者）
3. **技巧经验**：从审校/驳回反馈闭环沉淀（出处是评审事件而非文本引句），作者确认才转正；含**饱和度账本**（记录技巧近期使用频次，防口癖固化）；稳定验证后固化进分层规范文件（agent-instruction-layering 的领地）并 retired；默认本书作用域，作者显式确认才晋升作者级偏好库

### 冲突与修正

- 每张卡强制带出处（文本引句或事件链），记忆永远可回溯验证
- 新旧事实冲突**不自动裁决**：摆出两个修复方向的影响成本（顺正文改设定 vs 逆设定改正文），交作者裁决，复用现有审批闸门；裁决后自动更新记忆或生成回改任务清单
- 正文为准原则：已写正文 > 设定（既成事实优先于意图）
- 修正传播：改卡时报告"哪些章节引用了该记忆"（结构化存储的引用关系可查询）
- retired 不删行（留痕，同"角色只能退场不能删除"哲学）

### 召回与整理

- **注入召回（被动）五件套**：本章出场角色卡（复用活跃快照）+ 活跃伏笔 + 相邻章新事实 + 当前卷 planned 设定 + 本书技巧卡（含饱和度）；体量预算受控，近层优先
- **检索召回（主动）双通道**：FTS5 全文 + 结构化过滤（实体/类型/状态/章节范围）
- **权重三信号**：引用频次 + 近因 + 确认级别（可解释规则，不搞学习）
- **整理三触发**：事件驱动为主（章通过时顺手）+ 阈值触发（注入超预算）+ 定时兜底（僵尸卡清扫）
- **风险分级**：去重/同义合并自动执行可撤销；删除/降级/跨实体合并过审批
- **合并升级通道（三条，全部单向、全部过审批、原卡 retired 留痕）**：自由事实碎片→正式实体条目；计划设定→落文正文事实；技巧经验→分层规范文件
- **多语言原则**：事实卡保留原文语态，不做翻译/改写归一（引句必须对得上原文）

### 系统提示词

- 起草纪律（借 OpenHands 计划 stance）："先查记忆再动笔"；注入召回包 + 工具检索的分工写入 system prompt

### 外部参照（Hindsight 的三个吸收点）

调研 vectorize-io/hindsight（51.8k stars，LongMemEval SOTA）后确认**不引入**（独立 Python 服务 + PostgreSQL，与 Bun/SQLite 本地优先路线冲突；且其通用对话记忆能力对写作为是过度设计），但吸收三个设计：
1. Mental model 的"启动页"形态 → 注入包物化视图
2. Observations 的证据计数 → 实体卡 `proof_count` 字段
3. 多语言原样保留 → 中文语料天然成立，写入设计原则防未来改写归一

## Impact

- **受影响包**：`novel-store`（自由事实表、技巧卡表、状态字段、FTS5 虚表、物化注入包）、`plugin`（流水线挂钩：起草前注入、登记、审计校准、通过预计算）、`core`（记忆查询/登记工具注册）、`opennovel`（API 暴露）、`app`（记忆查看/编辑/裁决界面，远期）
- **数据兼容性**：纯新增表/字段 + 既有表加列（planned/established 落文状态），不改既有数据语义；FTS5 虚表新增需迁移脚本
- **依赖关系**：无前置 change；与 agent-task-subagent 协同（审校子代理查记忆/技巧卡）、与 agent-instruction-layering 协同（技巧固化的落点），均不阻塞
- **优先级理由**：对写作质量的直接贡献最大，且无法从上游移植、必须自研，越早立项越早积累

## 非目标

- 不做向量库/embedding 检索（FTS5 + 结构化查询先验证够不够；检索键是实体/章节/编号，非语义相似度）
- 不引入 Hindsight 等外部记忆服务（调研结论：吸收设计，不引入实现）
- 不做跨书记忆共享与自动全局晋升（作者级偏好库是显式登记的独立小存储）
- 不做记忆的自动遗忘/衰减策略（只增不删 + retired 留痕，人工清理）
- 不在本变更内改 37 维审计的维度定义（记忆沉淀作为审计产物的衔接点另议）
- 文风统计基线不进记忆（语料现算的 computed metric，记卡会漂移）
- 不做 agent 主动打"重要"标记的加深机制（先观察注入召回够不够）
