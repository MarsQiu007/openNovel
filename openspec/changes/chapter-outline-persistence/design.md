## Context

章纲文件已经形成稳定的 `chapter-{n}.md` 命名，插件工具、写作快照和服务端大纲面板各自读取文件。`chapters` 表已经承载章节元信息和正文，缺少的是章纲正文列。旧项目无法假设已有数据库包含该列，也不能要求一次性手动迁移。

## Goals / Non-Goals

**Goals:**
- 让数据库成为章纲权威来源，文件降级为兼容产物。
- 支持旧项目读取时懒导入，避免一次性迁移脚本。
- 覆盖生成、读取、WebUI 编辑和写作快照四条主要链路。
- 保持总纲/卷纲现有存储不变。

**Non-Goals:**
- 不实现章纲版本历史、diff 或章纲编辑器。
- 不把总纲/卷纲入库。
- 不删除或重命名旧 Markdown 文件。

## Decisions

### D1: 使用 chapters.outline 列，而不是独立表
在 `chapters` 表添加可空/默认空字符串的 `outline` 字段。章纲与章节一一对应，生命周期完全一致。

**理由**：独立表会引入额外 join 和 upsert 逻辑，但没有版本或多条草稿需求；列是最直接的持久化位置。

### D2: 数据库优先，文件懒导入
读取工具先查数据库列；为空时按章节序号读取 `.novel/outlines/chapter-{n}.md`，读取成功后写入数据库。读取失败返回空，不抛出阻断异常。

**理由**：一次性迁移需要扫描所有项目目录且容易在启动时失败；懒导入只触碰实际使用的章纲，失败时仍可重新生成。

### D3: 写入采用数据库 + 文件双写
`generate_chapter_outline` 和 WebUI 章纲保存先写数据库，再同步写 Markdown。文件写失败不应覆盖数据库成功结果，但应返回或记录可观察提示。

**理由**：数据库解决源头持久化；双写避免旧文件被后续流程读到过期内容，也降低回滚和外部工具兼容成本。

### D4: 服务端大纲面板复用同一读取规则
`getOutlineBundle` 的 chapters 部分改为数据库优先、文件兜底；`updateOutline` 的 section=chapter 写数据库并同步文件。master/volume 继续只处理文件。

**理由**：前端契约无需变更，仍使用 `chapterId`（当前为序号字符串）和 `markdown` 字段。

## Risks / Trade-offs

- [文件与数据库短暂分叉] → 统一先写数据库再同步文件，读取始终数据库优先。
- [懒导入在并发工具调用时重复执行] → 写入为幂等 UPDATE；同一内容重复导入无业务影响。
- [文件写失败可能被忽略] → 数据库仍是权威来源；工具输出或服务端日志提供可观察性。
- [空模板被当作有效章纲] → 沿用现有“待填写占位符视为缺失”的判断，避免裸写。

## Migration Plan

1. `CREATE_TABLES_SQL` 新库直接包含 `outline`；`migrate.ts` 用 `PRAGMA table_info(chapters)` 为旧库补列。
2. 插件章纲生成/读取和写作快照切到数据库优先。
3. 服务端大纲 bundle 与章纲编辑切到数据库优先、文件兼容。
4. 新代码通过单元测试覆盖新库、旧库和文件导入路径。
5. 回滚：新增列可保留；隐藏文件双写后系统仍可运行。
