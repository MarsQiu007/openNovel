# Proposal：tool-insight-log-hygiene

## Why

工具改进日志现在把「运行期是否存在问题」与「每个 Location 启动」绑在了一起：空的共享日志根会不断生成只有 0 问题索引的目录，复测临时项目也会留下哈希目录；同时多个插件实例可能重复消费同一批事件，导致同一证据被写入多份。这会让用户把真实的改进信号淹没在空目录和重复记录里，也削弱了自我优化数据的可信度。

## What Changes

- 将 tool-insight 的落盘从「启动即初始化」改为「按需落盘」：无证据、无问题文档、无复测记录、无负反馈信号且无待处理任务时，不创建索引、锁目录、证据文件或空日志根。
- 将复测临时 Location 与常规写作 Location 的日志边界分离：复测遥测只归属原问题与复测运行，不为每次临时运行创建新的常规项目日志根。
- 收紧事件归属与记录去重：同一事件由明确的采集归属方消费一次；客观证据和负反馈信号的稳定标识在存储层唯一，避免多实例复制、同根重复追加和重启重放。
- 增加轻量负反馈信号层：用户对 LLM 结果、工具行为或流程表达明确负面评价时，先用本地确定性规则记录由稳定枚举和会话/提示引用构成的结构化信号，不保存完整对话原文、文件附件或小说正文。
- 为负反馈提供确认升级路径：同类重复只作为提示；用户明确要求或确认影响后，信号才升级为现有 `user_report` 问题文档。普通负反馈保持为信号，不自动建完整 issue 或发起归因模型请求。
- 保留证据先行原则：客观证据仍可先于模型分析保存，但空状态不再产生用户可见的日志骨架。

## Capabilities

### New Capabilities

- 无

### Modified Capabilities

- `tool-insight-log`: 修改日志根、空状态落盘、复测隔离、事件归属去重、证据/信号唯一性，以及用户负反馈采集/升级的行为要求；不改工具改进日志的整体能力边界。

## Impact

- 主要影响 `packages/plugin` 中 tool-insight 的采集、整理、复测编排和 `tool_insight` 主动入口。
- 可能影响 `packages/novel-store` 中路径解析、JSONL 追加与读取辅助。
- 可能影响 `packages/core` 中内部会话 purpose 向插件上下文的传播；需要避免插件跨项目重复消费事件。
- 不修改写作工具的业务语义，不新增数据库表，不改变现有问题文档格式；旧目录中的历史文件保留只读兼容。
- 涉及负反馈信号时，需要处理会话消息或反馈意图与 tool-insight 的边界，必须遵守现有隐私白名单和脱敏截断规则。
- `docs/tool-insight.md` 需要补充信号文件、隐私边界和确认升级说明。
