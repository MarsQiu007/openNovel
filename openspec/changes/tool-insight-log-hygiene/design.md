# Design

## Context

当前 tool-insight 的启动对账、索引重建、锁目录创建和复测临时 Location 都会在没有真实问题时产生工件。事件采集又按插件实例运行，多个 Location 可能同时消费同一批全局会话事件；现有的去重只发生在问题文档内，JSONL 证据层本身没有唯一性约束。用户负反馈目前只能通过显式 `/evaluate` 入口进入 `tool_insight`，普通对话中的「不对 / 错了」不会形成可聚合信号。

相关实现分布在 `packages/plugin/src/tool-insight`、`packages/novel-store/src/evaluate-insight.ts`、`packages/plugin/src/novel-writer-v2.ts` 和复测编排模块；日志仍保持本地文件形态，不新增数据库表。

## Goals / Non-Goals

**Goals:**

- 把空状态、索引、锁和日志根的创建收敛到「有真实记录才落盘」。
- 让复测临时 Location 不再污染共享日志目录。
- 用稳定证据标识在存储层去重，防多实例与崩溃恢复重复追加。
- 将会话/项目归属作为日志根和事件归属的依据，而不是把所有事件都复制到每个活跃 Location。
- 把「不对 / 错了」这类负反馈变成低噪声信号，并提供显式确认升级为 `user_report` 的路径。

**Non-Goals:**

- 不重写问题文档格式，不引入数据库表或云端上报。
- 不自动删除旧目录中的历史空根；旧数据只读兼容。
- 不把每日汇总作为新的 source of truth。
- 不让负反馈信号层保存完整对话原文、完整章节正文或绕过现有隐私白名单。
- 不改变写作反馈意图协议在正文修订中的既有职责。

## Decisions

### 1. 空状态探测先行，落盘按需创建

启动对账先读取现有日志根和问题目录，只有发现真实证据、问题文档、复测记录或待处理任务时才进入锁与重建流程。日志根、锁目录、索引和证据文件只在写入第一条真实记录时创建。索引保持派生视图：没有问题文档时不写空索引。

选择这种方案而不是「启动时统一初始化」是因为后者会把健康状态也变成可见噪音。备选的「保留空索引以便 UI 显示」不必要，UI 可以把缺文件视为零问题。

### 2. 日志根按会话项目归属解析

事件采集时先从 `session.next.created` 维护会话到项目归属的有界映射；证据和负反馈信号按该归属解析日志根，而不是按每个插件实例的 Location 解析。无法确定归属的会话不采集。这样同一事件只会写入同一个项目根，避免多个 Location 复制。

选择会话归属而不是进程级单例，是因为后者无法覆盖桌面端与 CLI 并存的多进程场景。日志根仍然保留项目隔离语义；`global` 会话只进入专门的全局根，不会复制到每个小说项目根。

### 3. 复测临时 Location 带 internal purpose 标记

`startBackground(mode: "retest")` 已经登记 tool-insight purpose；把这个 purpose 传播到临时 Location 的插件上下文中，插件在启动时识别该标记并跳过常规采集与启动对账。复测遥测仍写回原问题的 `runs/<fingerprint>.jsonl`，临时项目只承载隔离执行所需的数据库和夹具。

选择显式 purpose 标记而不是根据临时目录路径猜测，是因为后者脆弱且难以测试。备选的在临时 `opennovel.json` 中写禁用开关不符合当前「toolInsight 是全局设置」的约束。

### 4. 证据标识在存储层去重

证据追加在锁内先读取现有标识集合，发现相同证据 ID 时直接跳过追加；随后才执行尾部撕裂修复和追加。这样即使多实例或多进程同时消费同一事件，锁会把并发串行化，第二个写入者会看到既有 ID 并放弃。

选择存储层去重而不是只依赖问题文档去重，是因为 JSONL 是客观证据的原始 sink；文档层去重无法阻止同一文件出现重复行。备选的 SQLite 索引可以后续引入，但当前规模下 JSONL + 锁内读取已足够。

### 5. 负反馈用独立低噪声信号文件

新增 `signals.jsonl` 作为负反馈信号层，记录稳定信号 ID、时间、目标范围、反馈类别、session/turn 引用和发生实例 ID。检测只消费会话提示文本以判断是否存在负反馈，不把提示文本、完整对话或章节正文写入信号层。可以使用 `session.next.prompted` 这类已有事件作为输入，不需要新增宿主事件类型。

选择独立 JSONL 而不是直接写入 `evidence.jsonl`，是因为负反馈不总是工具失败证据，过早建 issue 会制造噪声。选择不保存文本摘要，而不是自动脱敏保存一段文本，是因为「不对 / 错了」的真实语境需要用户确认后才值得持久化。用户确认升级时，仍走现有 `tool_insight` 的 `feedback` 白名单和脱敏截断路径。

### 6. 负反馈信号与 issue 解耦

信号文件只负责计数和聚合；升级为 `user_report` 时由用户确认或显式记录入口触发。升级时把信号 ID 关联到问题文档，但不把信号本身当作完整证据文本。同一发生实例在信号和 issue 中保持一致，避免重复计数。

选择「确认升级」而不是高频自动建档，是因为一次负反馈可能只是风格纠偏，重复出现也不必然代表工具缺陷。

## Risks / Trade-offs

- [会话归属缺失导致漏采] → 未观察到 `session.next.created` 时按丢弃处理，并在 UI 或诊断层保留可解释性；不使用当前 Location 兜底。
- [负反馈误报] → 信号层只记录类别和范围，不自动建 issue；升级必须经用户确认。
- [隐私压力] → 信号层不存原文；升级后的文档继续走既有脱敏、截断和正文授权规则。
- [旧目录残留] → 本次不自动清理历史空根，避免误删用户数据；后续可提供显式维护命令。
- [JSONL 长度增长] → 锁内读取去重成本随文件增长；如果后续成为瓶颈，再引入本地索引或 SQLite，不在本 change 提前扩展。

## Migration Plan

- 不迁移数据库，不改公开协议，不需要重新生成 SDK。
- 旧日志目录保留；新逻辑只影响新证据、新信号和新复测运行。
- 上线后空项目不再产生新空根；已有空根仍保留。若用户需要清理，可另行提供显式维护入口。
- 回滚时恢复原有启动初始化即可，已写入的新 `signals.jsonl` 保留为普通本地文件。
