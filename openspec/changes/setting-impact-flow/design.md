## Context

openNovel 已有一套基于 `entity_refs` 和 `pending_updates` 的级联一致性机制，`manage_characters` 和 `update_setting` 的部分字段会扫描引用并创建任务。但真实设定修改入口分散在角色管理、世界观更新、关系创建、候选区接受/合并、observer 状态提交等路径中；各路径对影响分析、旧值捕获、任务生成和输出的处理不一致。已有机制也主要识别名字精确出现，难以覆盖“力量体系变化影响角色能力”“伏笔状态影响后续大纲”等语义或结构依赖。

本提案不推翻现有机制，而是把 `entity_refs`、`pending_updates`、`description_history` 和候选区整合到一个统一影响面流程下。

## Goals / Non-Goals

**Goals:**

- 建立唯一的 `SettingImpactService`，让所有正式设定修改共享同一套影响计划、任务生成和报告。
- 让 AI 在修改前能看到影响计划，在修改后能看到待处理任务。
- 把确定性引用、结构性依赖和语义建议分层处理。
- 保持写作门禁：有未处理任务时不能继续制造新的漂移。
- 保留旧数据兼容，避免破坏现有小说库。

**Non-Goals:**

- 不做完美自然语言理解。
- 不自动重写整本书。
- 不在本提案中重构 UI。
- 不替换现有候选区和审计流程。

## Decisions

### 1. 用一个服务统一所有修改入口

新增 `SettingImpactService`，负责：

- 规范化变更意图。
- 读取旧值。
- 执行真实变更。
- 重建引用。
- 计算影响计划。
- 生成任务。
- 返回统一报告。

现有工具如 `manage_characters`、`update_setting`、`save_novel_settings`、`create_relationship`、`organize_settings`、候选区接受/合并、observer 状态提交仍然保留原工具名，但内部必须调用该服务或复用其任务生成逻辑。这样可以避免每个工具各写一套“级联提醒”。

### 2. 影响计划分三层

1. **确定性引用**：基于 `entity_refs`、章节正文、角色描述、卷摘要、章纲等文本的精确或可归一化命中。可直接生成任务。
2. **结构性依赖**：基于数据库外键或稳定关系，例如角色与关系端点、伏笔与章节、剧情线与章节、弧光与角色。可生成任务或提示。
3. **语义建议**：由 AI 根据变更内容和相关上下文提出，例如力量体系变化可能影响角色能力描写。语义建议必须等待用户确认，不能自动执行。

这样第一版可以保证“知道确定性影响”，同时给 AI 留出“发现间接影响”的通道。

### 3. 复用并扩展任务存储

优先复用 `pending_updates` 作为影响任务的持久化载体，必要时增量增加任务类型和结构化 payload 字段。`pending_updates` 继续表示“待处理影响”；`SagaSessionTable` 继续表示批量执行进度；`description_history` 继续记录字段历史。

不新建一套平行的任务系统，避免出现两份“待办”和两套门禁。

### 4. 输出必须是结构化影响报告

所有设定修改工具返回中都应包含：

- `impact_plan`：变更对象、字段、旧值摘要、新值摘要。
- `findings`：确定性影响、结构影响、语义建议。
- `task_count`：新增任务数量。
- `pending_count`：当前未处理任务数量。
- `blocked_writing`：是否阻止继续写作。
- `next_actions`：建议调用的影响任务处理动作。

该结构先通过工具输出和提示词暴露；后续 UI 可以直接复用。

### 5. 语义建议必须显式确认

语义建议不能直接变成“已完成”或“待执行”的正式任务。它先以 `requires_confirmation` 状态暴露；用户确认后才进入执行队列，用户拒绝则记录为已忽略。这样避免模型误判导致大范围重写。

### 6. 门禁保持简单

有未完成任务时，`write_chapter` 和 `revise_chapter` 继续被拦截。门禁提示必须包含：

- 未完成任务数量。
- 高优先级任务摘要。
- 查询和处理任务的入口。

用户明确跳过任务后，门禁才能因该任务解除。

### 7. 本地数据兼容

数据库迁移只做增量：

- 新字段允许空值或带默认值。
- 旧 `pending_updates` 记录继续可读。
- 旧 `entity_refs` 不重建也能继续工作。
- 用户可以按需触发全量引用重建。

不要求用户迁移或重写既有章节。

## Risks / Trade-offs

- [确定性扫描可能漏掉隐式依赖] → 语义建议和 AI 提示词兜底，但不自动执行。
- [语义建议可能误报] → 全部要求用户确认，确认后才生成任务。
- [统一入口改动范围较大] → 先保证核心设定类型接入，再逐步覆盖更多工具路径。
- [旧数据库缺少新字段] → 增量迁移和空值兼容；旧任务继续可见。
- [影响报告过长] → 输出按优先级和数量截断，详细列表保留在元数据中。

## Migration Plan

1. 先实现服务与数据结构，不改现有工具行为。
2. 接入 `manage_characters` 和 `update_setting` 这两个最高频入口。
3. 接入世界观、关系、伏笔、剧情线和候选区路径。
4. 接入 observer 状态提交路径。
5. 最后补齐提示词、测试和文档。

每个阶段都必须保持旧工具可调用，并确保未接入路径不比现状更差。
