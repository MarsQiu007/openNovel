## Context

云盘同步基于 SQLite `vacuumInto` 全库快照，`content_hash` 覆盖所有非 FTS5 表的行数据。当前章纲在 `chapters.outline` 中已被同步，但总纲（`master-outline.md`）和卷纲（`volume-{n}.md`）存放在文件系统中，不被快照覆盖——跨设备时大纲丢失。同时 DB + 文件双写（章纲）引入了一致性维护成本。

## Goals / Non-Goals

**Goals:**
- 让总纲、卷纲、章纲统一存储在数据库中，DB 是唯一权威来源。
- 总纲和卷纲自动被云盘同步覆盖。
- 消除 DB/文件双写的分叉风险和文件 I/O 错误处理。
- 旧项目的 Markdown 文件通过懒导入写入数据库。

**Non-Goals:**
- 不做大纲编辑器 UI 增强。
- 不做大纲版本历史或 diff。
- 不删除用户磁盘上的旧 Markdown 文件（成为无害残留）。

## Decisions

### D1: `novels.master_outline` 列存储总纲
总纲跟小说是 1:1 关系，生命周期一致。跟 `chapters.outline` 同模式，直接加列，不建独立表。

**理由**：没有多种大纲类型的复用需求，独立表会引入额外的 upsert 逻辑。将来如果出现多种类型再拆不迟。

### D2: `volumes.outline` 列存储卷纲
卷纲跟卷记录 1:1 对应，跟 `chapters.outline` 完全同构。

### D3: 懒导入旧文件
读取时 DB 列为空就读一次对应的 Markdown 文件并写入 DB，之后不再碰文件。不做一次性迁移脚本。

**理由**：跟章纲的已验证模式一致，避免启动时扫描所有项目目录导致失败。

### D4: 彻底移除文件读写
所有大纲的生成、读取、编辑均走数据库列。`.novel/outlines/` 目录不再被任何代码读写。旧文件留在磁盘上不清理。

**理由**：云盘同步是 DB 快照机制，文件从未被同步。去掉文件消除了双写分叉风险，简化了错误处理。

## Risks / Trade-offs

- [旧文件未被导入前被删除] → 懒导入在首次读取时立即写入 DB；只有当用户在升级后、首次打开大纲前手动删除文件才会丢失（边缘场景，可接受）。
- [某些外部工具依赖文件] → 未发现代码库外的文件消费者；如有，需要在实施时确认。
- [`chapter-outline-persistence` spec 需同步修改] → 修改 capability 移除双写和文件兜底要求。

## Migration Plan

1. `novels` 和 `volumes` 表新增列，旧库用 `PRAGMA table_info` 补列。
2. 插件工具（生成/读取大纲）切到数据库读写。
3. 服务端大纲 bundle 和编辑切到数据库读写。
4. 章纲读取移除文件兜底，简化为 DB 唯一来源。
5. 懒导入逻辑覆盖总纲、卷纲和章纲的旧文件。
6. 回滚：新增列可保留；恢复写文件不影响已有 DB 数据。
