## Context

当前实现把「整个字段 trim 后超过 200 字且不含任何换行」作为长文本硬校验，并把同一条件复用到设定整理分析。这个条件有两个问题：一是 200 字对角色 description、关系 description 等连贯段落过于激进；二是它只检查全文是否包含换行，一个 700 字的段落只要旁边还有短段落就会被放过。

设定写作和整理已经统一要求纯文本、禁止 Markdown，并把显式换行规范化为 `

`。前端阅读器和设定批注依赖段落边界，因此长文本仍需要分段，但阈值应该落在“可读性问题”而不是“普通段落长度”上。

## Goals / Non-Goals

**Goals:**

- 用单个规范化段落长度作为长文本硬校验依据。
- 允许 200–600 字的完整语义段落存在。
- 保留按主题分段和约 80–220 字的 AI 写入引导。
- 让整理分析准确指出超长段落，而不是把长字段整体误报。
- 保持问题类型和 API 契约稳定，避免不必要的前后端改动。

**Non-Goals:**

- 不限制字段总字数。
- 不迁移既有数据。
- 不引入用户配置阈值。
- 不放松纯文本和 Markdown 拦截规则。
- 不改变设定批注锚点模型。

## Decisions

### D1: 以规范化段落的最大长度为校验单位

写入校验应先把显式换行规范化为 `

`，再按段落检查；任何一个段落超过 600 字才拒绝。字段总字数只作为提示上下文，不作为失败条件。

这个语义能同时覆盖两种情况：整段无换行的 650 字文本会被拒绝；已有多个段落但其中一个 700 字段落也会被拒绝。300 字的连贯段落则可以正常保存。

备选方案：

- 只把阈值从 200 提高到 600，但仍检查全文是否含换行——实现最小，但会继续漏掉“多段内容中的超长段落”。
- 按字段总字数限制——会把多个合理短段落组成的字段误判为问题。
- 不做硬校验，只靠提示词——无法保证新写入数据具备可锚定的段落结构。

### D2: 固定 600 字硬阈值，80–220 字作为提示目标

600 字是硬性可读性上限；80–220 字是 AI 写入的排版目标。两者分开后，模型会倾向于生成更易读的段落，但用户或模型仍然可以保留一个 300–500 字的连贯描述段。

选择 600 字而不是 300/400 字，是为了显著减少当前面板中 200–500 字角色描述的噪音。600 字在设定中心的阅读宽度下已经明显接近“墙式文本”，足以触发整理建议。

备选方案：

- 保持 200 字——继续产生大量误报。
- 400 字——仍可能把一些完整角色刻画误判为问题。
- 可配置阈值——增加配置面，当前还没有证据表明不同项目需要不同阈值。

### D3: 复用 `long_single_paragraph` 问题类型

不新增问题类型或 API 字段，避免 schema、Protocol、生成客户端和整理面板一起改动。其语义从“全文过长且无换行”收窄为“存在一个超长段落”。证据文案改为标明字段和该段字数，用户可以知道要拆哪一段。

备选方案：

- 新增 `long_paragraph` / `paragraph_style_hint` 类型——语义更精确，但会扩大 schema、协议和 UI 变更范围。
- 继续用全文条件——与新的写入校验不一致。

### D4: 自动分段只处理超长段落

自动生成分段计划时，应保留既有的短段落和顺序，只把超过 600 字的具体段落拆开。拆分优先在句号、感叹号、问号后进行；目标段落长度控制在约 80–220 字，避免现在按约 80 字机械断段造成的碎片化。

如果超长段落中没有可用的中文句末标点，自动计划可以不生成该项操作，只保留 analyze 建议等待 AI 或用户处理。

备选方案：

- 对整个字段重新分段——会改变用户已有段落结构，风险更高。
- 每句一段——段落过碎。
- 无标点时强制切——可能把名字、数字或引用切断。

## Risks / Trade-offs

- [600 字仍是启发式阈值] → 先固定阈值并补充测试；如果实际使用仍有明显误报/漏报，再评估配置化。
- [旧数据中的 600 字以下长单段不会再被标记] → 这是本提案的目标；用户仍可手动分段，且超过 600 字的段落仍会提示。
- [自动分段可能改变句间停顿] → 只拆超长段落、只使用句末标点、保留其他段落；计划仍需 dry run 和用户确认。
- [`long_single_paragraph` 名称不再是字面意义的“全文单段”] → 通过证据文案和规格说明澄清；为兼容性保留现有问题类型。

## Migration Plan

无数据库迁移和 API 契约变更。部署后，新写入校验和整理分析立即使用新阈值；既有数据不变。回滚时 revert 对应实现提交即可。

实施时应从共享设定文本模块开始调整校验，再更新提示词和整理分析/计划生成，最后补充 plugin 定向测试并运行 typecheck / lint。
