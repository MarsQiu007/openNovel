## Context

驳回目前是纯状态更新：服务端把章节置为 `rejected`，写入 human review，然后返回。会话路由、绑定会话查找、懒创建和 prompt 发送能力已经在前端工作台存在，批注执行也使用同一链路。director/pipeline 已经有“重写第X章 / 驳回后重写”分支，因此不需要新增服务端编排端点。

## Goals / Non-Goals

**Goals:**
- 保持驳回语义不变，默认不自动派工。
- 在用户显式确认后，把驳回上下文交给最近的绑定写作会话。
- 复用会话查找、懒创建、绑定和 prompt 发送链路。
- 保证驳回先落库，AI 衔接失败不会破坏审批结果。

**Non-Goals:**
- 不由服务端在审批 API 内自动发送 prompt。
- 不改 EDIT 分支，不新增驳回原因结构化表单。
- 不等待 AI 重写完成；不把重写结果同步回审批面板。

## Decisions

### D1: 前端确认后发送，而不是服务端自动派发
在驳回确认面板增加默认关闭的显式选项。用户确认后，前端先调用现有审批接口；成功后再向绑定会话发送结构化指令。

**理由**：驳回可能是“记录问题后自己改”，自动派工会剥夺用户控制权。前端确认可以在 UI 中明确表达意图；服务端保持审批状态机纯净。

**替代方案**：REJECT 分支自动调用 Session prompt。拒绝原因：服务端需要理解会话路由和用户意图，扩大审批 API 副作用，也不利于失败回滚边界。

### D2: 指令按“驳回后重写”结构生成
prompt 包含 novel_id、chapter_id、chapter_title、chapter_order、action=rewrite_after_reject 和驳回意见，并明确要求走既有“驳回后重写指定章节”流程。

**理由**：director/pipeline 已经有该分支。稳定字段比只写一句“重写第X章”更能避免标题歧义和漏传反馈。

### D3: 复用最近绑定会话与懒创建
优先选择未归档、非子代理的最近绑定会话；没有会话时创建新会话、绑定小说再发送。会话忙碌时不额外加锁，依赖 SessionV2 的排队/继续语义。

**理由**：这是批注执行和首条消息已验证的链路，避免引入另一套会话路由规则。

### D4: 发送失败不回滚驳回
审批请求成功后，前端刷新章节和审批数据。后续会话创建或 prompt 发送失败只显示“驳回已保存，AI 重写指令发送失败”。

**理由**：审批确认和 AI 派工是两个副作用。回滚驳回会制造更难处理的复合事务；显式提示让用户可以稍后重发。

## Risks / Trade-offs

- [用户误勾选] → 默认关闭，并使用独立中文标签和确认动作。
- [指令被会话上下文稀释] → 使用结构化字段并直接点名“驳回后重写指定章节”分支。
- [会话不可用] → 无会话时懒创建；仍失败则提示，但驳回状态已保留。
- [用户希望静默驳回] → 默认不勾选，完全保持现有行为。

## Migration Plan

1. UI 增加默认关闭的 AI 接手选项。
2. 前端在审批成功后按选项发送结构化 prompt。
3. 依赖现有 director/pipeline 分支，不修改审批服务端。
4. 回滚：隐藏选项或取消发送逻辑，审批流程回到原有静默驳回。
